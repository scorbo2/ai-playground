# Match 3 — Code Review

Two Python/Pygame implementations of a Match 3 game, each generated by a different LLM from the same spec:

- **Match3-gemma.py** — generated by Gemma
- **Match3-qwen.py** — generated by Qwen

---

## Game Rules & Presentation Consistency

| Aspect | Gemma | Qwen |
|--------|-------|------|
| Board size | 8×8 ✓ | 8×8 ✓ |
| Cell/token sizes | 60px cell, 50px token ✓ | 60px cell, 50px token ✓ |
| Token shape | Circle with white border ✓ | Circle with white border ✓ |
| Token colors | Slightly off (`#00cc00` green, `#0066ff` blue) | Pure CSS values (`#00ff00`, `#0000ff`) |
| Selection highlight | Selected=dark green, neighbors=dark gray ✓ | Same ✓ |
| Invalid swap flash | Red cell highlight for 0.3s ✓ | Same ✓ |
| Red match penalty | Negative score ✓ | Same ✓ |
| Red match border flash | Yes ✓ | Yes ✓ |
| Chain scoring multiplier | **Linear** (1×, 2×, 3×, …) | **Exponential** (1×, 2×, 4×, …) |
| Match grouping for scoring | Connected components (an L/T-shape = one group) | Per-run (horizontal + vertical runs scored separately) |
| Overlay feedback text | Floating, fades + rises | Floating, fades + rises ✓ |
| Sidebar layout | Centered label + value blocks | Left-aligned "Label: value" |
| Restart button | Present, always clickable | Present, always clickable ✓ |

**The chain scoring multiplier and match grouping rules differ between the two implementations.** These divergences would produce different scores for identical play. Neither can be said to be "correct" without reference to the original spec.

## Bugs

### Match3-gemma.py

#### 1. Broken `Game` base class (architectural) 🔴
The `Game` class uses `async def` methods and `asyncio`, but the approach is fundamentally broken:
- `run()` calls `loop.stop()` inside the game loop, which kills the event loop on the very first frame.
- `handle_click()` calls `asyncio.create_task()` with no running event loop.

Gemma acknowledged this mid-file with a comment ("This is tricky in a game loop") and wrote a second class `GameSequential(Game)` to work around it with a timer-based approach. The `Game` base class is effectively dead code. Only `GameSequential` (the entry point) actually works.

#### 2. Frame-rate-dependent animation 🟡
`Token.update()` uses a lerp factor of `0.15` applied **per frame**, ignoring the `dt` parameter:
```python
self.curr_x += (self.target_x - self.curr_x) * lerp_factor  # dt unused!
```
Animations will run at different speeds depending on frame rate.

#### 3. Only one pending action supported 🟡
`GameSequential.schedule_action()` stores a single `pending_action`. A second call silently overwrites the first. This happens to work because each step in the match pipeline schedules exactly one successor, but it is fragile and could break if the logic is extended.

#### 4. New tokens skip the match-prevention check 🟡
`fill_empty_seq()` places freshly spawned tokens with a plain `random.randint()`, without calling `would_create_match()`. New tokens can arrive pre-matched and immediately trigger a cascade that wasn't caused by player input.

#### 5. Hacky token rendering 🟡
To account for the board offset, `draw()` temporarily mutates `curr_x`/`curr_y` on every token, then restores them:
```python
old_x, old_y = t.curr_x, t.curr_y
t.curr_x += BOARD_OFFSET_X
t.curr_y += BOARD_OFFSET_Y
t.draw(self.screen)
t.curr_x, t.curr_y = old_x, old_y
```
This is fragile; the correct approach is to pass the offset into `draw()`.

### Match3-qwen.py

#### 1. Level advance is never triggered — player cannot progress 🔴
`_check_level_advance()` is defined but **never called** anywhere in the update path. `_update_gravity_anim()` only calls `_check_game_over()`:

```python
else:
    self.chain_multiplier = 1
    self.state = STATE_IDLE
    self._check_game_over()   # ← _check_level_advance() missing here!
```

`STATE_LEVEL_COMPLETE` and `STATE_LEVEL_BEGIN` are therefore unreachable dead states. The score threshold is displayed but can never be met in a meaningful way — the game never advances to Level 2.

**Fix:** Add a call to `self._check_level_advance()` before or instead of `self._check_game_over()` when returning to idle (and only call game-over check if level wasn't advanced):

```python
else:
    self.chain_multiplier = 1
    self._check_level_advance()
    if self.state == STATE_IDLE:   # only if level didn't advance
        self._check_game_over()
```

Note: `_check_level_advance()` sets `self.state = STATE_LEVEL_COMPLETE` on success, so `state` must still be `STATE_IDLE` if it didn't advance.

#### 2. `NameError` crash in sound fallback 🔴
In `_load_sounds()`, if the `sfx/` directory is missing the fallback creates a silent sound:
```python
silent = pygame.sndarray.make_sound(
    pygame.sndarray.zeros((44100,), dtype=int16))  # ← int16 not imported!
```
`int16` is never imported (it's a NumPy type). This raises `NameError: name 'int16' is not defined` and crashes the game on startup whenever the sfx directory is absent.

**Fix:** Replace `int16` with `'int16'` (a string, which NumPy accepts) or add `import numpy as np` and use `np.int16`.

#### 3. Dead variable in `_update_level_complete` 🟢
```python
elapsed = pygame.time.get_ticks() - self.overlay_timer  # meaningless: ticks - countdown ms
```
`overlay_timer` is a countdown (decremented each frame), not a timestamp. `elapsed` is computed but never used. The method works correctly because the real check is `if self.overlay_timer <= 0`, but the dead variable is misleading.

## Code Quality

### Qwen — significantly cleaner

- **Clean state machine:** Named string constants (`STATE_IDLE`, `STATE_SWAP_ANIM`, etc.) with a single `update()` dispatching to well-named `_update_*()` methods. State transitions are easy to follow.
- **Unified board representation:** A single `board: List[List[Token | None]]` array. Token objects carry their own color, position, and animation state — no dual-array sync problem.
- **Rendering well decomposed:** `render()` delegates to `_draw_title_bar()`, `_draw_board()`, `_draw_tokens()`, `_draw_particles()`, `_draw_sidebar()`, `_draw_overlay()`. Each is focused and testable.
- **Consistent timing:** All animation timers use milliseconds (`dt_ms` from `clock.tick()`). Gravity animation uses a velocity-capped movement formula that is frame-rate-independent.
- **Good docstrings:** Every class and non-trivial method has a clear docstring.
- **Sound loading:** Graceful path resolution via `os.path.dirname(__file__)` + `os.path.join`.

### Gemma — workable but messy

- **Dual board arrays:** `self.board` (2D list of `int`) and `self.tokens` (2D list of `Token | None`) must be kept in sync. This is a classic source of subtle bugs and complicates every board-manipulation method.
- **Broken base class left in:** The dead `Game` class with its broken `asyncio` architecture adds ~350 lines of misleading code. The file reads as if Gemma changed approach halfway through and left the old attempt intact.
- **Mixed timing:** `Token.update()` uses a frame-rate-dependent lerp; the scheduler uses wall-clock seconds via `time.time()`; elsewhere `dt` (seconds) is passed from `clock.tick()`. No single consistent unit.
- **Inline nested function for sidebar drawing:** `draw_sidebar_item` is defined inside `draw()` and captures `y_off` from the enclosing scope, relying on Python closure semantics to read the updated value. It works, but is harder to follow than a simple helper method.
- **Match grouping more nuanced:** Gemma's `find_contiguous_groups()` uses BFS to find connected same-color components, which is arguably closer to how players perceive multi-directional matches (L/T-shapes as one "group"). Qwen's per-run approach is simpler but scores L/T-shapes lower.

## Summary

| | Gemma | Qwen |
|---|---|---|
| **Playable** | ✅ Yes (via `GameSequential`) | ✅ Yes (Level 1 only) |
| **Level progression** | ✅ Works | ❌ Broken — never advances |
| **Sound loading** | ✅ Graceful | ❌ Crashes if sfx dir missing |
| **Animation correctness** | ⚠️ Frame-rate dependent | ✅ Frame-rate independent |
| **Code clarity** | ⚠️ Confusing dual-class structure | ✅ Clean state machine |
| **Board representation** | ⚠️ Two arrays to keep in sync | ✅ Single unified array |
| **Rules consistent with each other** | ❌ Chain scoring and match grouping differ | ❌ (same) |

**Qwen has cleaner, better-structured code overall**, but has a critical gameplay regression (level advancement is entirely broken) and a startup crash risk. **Gemma's implementation is more playable end-to-end** despite its architectural messiness. Neither is bug-free, and they do not implement consistent game rules with each other.
