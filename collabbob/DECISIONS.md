# Decisions

What follows is a record of decisions made by the implementing LLM
to handle anything that the spec didn't make explicit.

## Stage 1 — Walking skeleton + tooling

- The three config files use the full key set from the spec sketch, with
  medium values as the base and easy/hard tuned per the dev plan (easy:
  generous economy and better starting ship stats with lighter fuel usage;
  hard: smaller fares, faster fuel burn, pricier upgrades, weaker starting
  ship stats). `win_credits` is the same 1,000,000 in all three files.
- The ambiguous two-element fare lists (`economy.cargo_fare_per_unit`,
  `economy.passenger_fare_each`) are interpreted as the minimum and maximum
  per-unit fare rates; a mission fare = units * rolled rate * far-destination
  multiplier (far-destination bonus applied as a multiplier on the rolled
  fare).
- The schema is enforced with pydantic models (`extra="forbid"` so
  unrecognized keys are fatal, required fields so missing keys are fatal);
  numeric fields accept ints and floats as written in the config.
- The stage-1 main loop is a no-op skeleton: fixed 1/60 step with a bounded
  accumulator (limit 5/60), real dt ignored, window created before the loop
  starts. UI/scene/game logic is added in stages 2 onward.
- ESC quits the stage-1 window (no title screen exists at this stage).
- `resources/title_screen.png` is generated by
  `scripts/generate_title_screen.py` (dark 1024x768 gradient) so the title
  screen background exists at startup.
- The headless test harness runs under `SDL_VIDEODRIVER=dummy` and
  `SDL_AUDIODRIVER=dummy` via the root conftest.py, plus a
  `config_factory` fixture and `pump_events`/`advance` helpers in
  `src/harness.py`.

## Stage 2 — Scene manager + title screen

- **Scene stack design**: a `SceneManager` holds a list-based stack of `Scene` objects.
  Only the top scene receives `handle_event()` and `update()`. All scenes are drawn
  bottom-to-top so modal overlays (e.g. the difficulty dialog) appear correctly layered
  over the scenes beneath them.
- **Difficulty dialog**: implemented as a `DifficultyDialog` scene pushed on top of the
  `TitleScene`. It draws a semi-transparent overlay so the title is visible behind it.
  Selecting a difficulty pops the dialog, then replaces the `TitleScene` with a
  `PlaceholderScene`, leaving a single-entry stack.
- **PlaceholderScene**: a temporary stub scene used as the Stage 2 gate target. It will
  be replaced by the full tactical display in Stage 4. ESC returns to the title screen.
- **Audio**: `AudioSystem` is a fail-soft singleton constructed in `main()` and stored on
  the `SceneManager`. Scenes access it via `self._manager.audio`. The confirmation beep is
  generated with `stdlib.array` + `pygame.mixer.Sound(buffer=...)` as required by the spec.
- **`FixedTimestepLoop` refactored**: the loop now accepts an optional `scene_manager` and
  `screen` parameter; `on_step` is kept for stage-1 backward compatibility. When a
  `SceneManager` is supplied, events are routed to it and it drives update + draw each frame.
- **Window caption** ("The velocity of escape") is set in `main()` via
  `pygame.display.set_caption()` once the display surface is created.


## Stage 3 — Pure model core (no pygame)

- **`GameState` takes a flat merged config dict**, not the loader's filename-keyed dict. `load_config()` returns `{filename: values}`; gameplay needs one difficulty's flat values, so tests extract `loaded["config_easy.json"]`.
- **Reverse-course frame count is derived from `turn_rate_deg_per_sec`** (default 180°/s → 3°/frame at fixed 60FPS → exactly 60 frames for a 180° flip). This keeps the behaviour config-driven rather than hard-coded.
- **Thrust caps velocity magnitude by rescaling**, not naive clamping: when the acceleration step would push speed over `top_speed`, the velocity vector is scaled down to land *exactly* on `top_speed`. Naive accumulation left it at `4.9999…`; rescaling yields exactly `5.0`.
- **Fuel burn** comes from `tactical.fuel_burn_per_frame` and is consumed once per thrusting frame. Reverse-course flips and inertial drift consume no fuel. Fuel is clamped to zero and has a clamping setter so it can be set/patched in tests.
- **Reverse-course is a pure rotation**: no thrust, no fuel, no velocity or position change. While flipping, left/right arrow rotation is ignored (the auto-flip takes priority).
- **Reverse-course restart semantics**: pressing Down while idle begins a flip from the current heading; pressing it again mid-flip resets the flip origin to the current heading and continues toward a fresh +180° target (so completion takes another full 60 frames, ending at `start + 210°` in the test).
- **Coordinate convention**: world coordinates are planet-centred — the planet sits at `(0, 0)` and the system boundary spans `[-system_pixel_size/2, +system_pixel_size/2]` on each axis. Positions/velocities are offsets from the planet. This is the convention `world_to_screen` in Stage 4 will map to screen space.
- **Heading** is stored as a raw degree value and normalised to `[0, 360)` via `heading_degrees`. Completion checks use a small epsilon (`1e-9`) so float drift doesn't cause a flip/thrust to stop one frame short.

## Stage 5 — Input layer

- **`src/input.py` owns the raw-key → control/action translation.** The `InputLayer` consumes pygame `KEYDOWN`/`KEYUP` events via `feed_event()` and, once per real frame, exposes a `ControlFrame(thrust, left, right, reverse_edge)` plus a list of discrete `Action` objects. This cleanly separates key handling from simulation: the tactical scene feeds raw events into the layer, then asks the layer to drain a frame.
- **Binding table (edge-triggered actions):** `space` → `fire`, `m` → `open_map`, `j` → `jump`, `l` → `land`, `t` → `scan`, `escape` → `exit_game`. Left/right/up are *level* control signals; down is an *edge* signal (rising edge only, so holding does not re-trigger).
- **`fire` is level-hold**: pressing and holding space emits one `fire` action per drained frame while held, supporting a configurable rate-of-fire later. The other five bindings are strictly edge-triggered (emit once per physical press).
- **Input-lock flag:** when set (a jump is in progress), `drain_frame()` returns `None` for the control frame and an empty action list — every control and binding is suppressed for that frame, and any queued actions are discarded so they cannot leak to the next frame.
- **`ControlFrame` vs `GameState.InputFrame` duplication:** these are two small 4-boolean dataclasses living in different layers. I deliberately did *not* have the pure model import `input.py` (which imports pygame), because Stage 3's gate requires the model core to stay free of pygame. The tactical scene maps `ControlFrame` → `feed_input(**kwargs)`. Documented here to avoid "silent" duplication.
- **TacticalView wiring:** `handle_event()` now delegates to `self.input.feed_event(event)`; `update()` drains the frame, feeds controls into `game_state`, and dispatches actions through `on_action()`. Actions that belong to later stages are accepted but currently routed to a no-op (with an optional confirm beep) so nothing half-built is wired up.

## Stage 4 — Tactical view, camera, starfield

- **`TacticalView.__init__(self, manager)`** takes the manager at construction (unlike the title/difficulty scenes, which set up state in `on_enter`). The tactical view needs its config/game state/ship sprite immediately, and the stage-4 tests construct it directly. `on_enter` is now a no-op passthrough so there is no double setup when the scene manager pushes/replaces it.
- **Flat config access**: `TacticalView` reads the flat merged config via `manager.configs["config_easy.json"]`, matching how `main.py` wires the loader's filename-keyed dict to gameplay. `GameState` still receives that flat dict (per the Stage 3 decision). *(**superseded** — see "Stage 6 review fixes" item 8: hard-coding the easy file made every difficulty play the easy game.)*
- **View geometry is hard-coded in code** (`VIEW_WIDTH = 683`, centre at `(341.5, 384)`), because window size/dimensions are chicken-and-egg exceptions per the spec and must not depend on the config being loaded first.
- **Starfield recycling**: a star is recycled only when it goes *strictly outside* the visible `[-half_extent, +half_extent]` box; respawn places it inside an inset box of `[-(half_extent - spawn_margin), +(half_extent - spawn_margin)]`. With `spawn_margin` equal to a controlled movement distance, no star ever leaves during that movement, so the "shift left by exactly delta" invariant holds deterministically without recycling interference. Default `spawn_margin = 0` keeps the full view populated in gameplay.
- **Planet colour** is chosen deterministically from `planet_diameter % len(_PLANET_COLORS)` (dicts are unhashable, so no `hash()` on config).
- **Ship sprite**: a cached, procedurally drawn blocky cargo shuttle sized to `player_ship.length` × `player_ship.width`; each frame a rotated copy is blitted centred on the ship's world position mapped through `world_to_screen`.

## Stage 6 — HUD + minimap + landing prompt

> **Historical record.** The first Stage 6 revision contained real defects that the
> stage gate did not catch. Where a bullet below contradicts the
> "Stage 6 review fixes" section at the end of this file, **the review-fixes section
> wins**; superseded bullets are tagged inline rather than deleted so the reasoning
> that produced them stays visible.

- **HUD is the right third of the window** (341 px wide = `1024 - 683`), implemented as a separate `HudView` scene pushed *after* `TacticalView` in the stack, so it draws on top and owns only the region `x >= VIEW_WIDTH`. This keeps the game view and HUD cleanly separated; each scene clears only its own region. *(**superseded — this froze the game**: only the top scene receives `handle_event()`/`update()`, so a passive HUD on top of the stack swallowed every keystroke. The HUD is now a component of `GameScene`; see review fix 1.)*
- **`TacticalView.draw()` now fills only the left game-view rectangle** (`[0, VIEW_WIDTH]`) instead of the whole surface. Previously it wiped the entire screen black each frame, which would clobber the HUD drawn by `HudView`. Overlays added later (e.g. jump feedback) are confined to the game-view rect for the same reason.
- **HUD palette and border styling live in code**, not config — even though the Stage 6 prose says "palette from config". The overarching spec rule explicitly lists "colors-as-defaults" as something that should live in code, so I kept a small `_HudPalette` (dark background, light-green text/bars, gray 2px borders) in `hud.py` and did *not* add a `hud` section to the config schema. Adding config keys would have required touching the pydantic model + all three shipped configs + `base_config()`, for styling that is better owned by presentation code. Recorded here so this "palette from config" wording isn't silently dropped.
- **Pure functions are the testable core.** `bar_width()`, `navigation_status_text()`, `navigation_is_bold()`, `planet_arrow_direction()` (unit vector ship→planet), `arrow_quadrant()` (all four quadrants), and `minimap_scale()`/`is_planet_off_map()` live in `hud.py` with no pygame dependency, so the gate's bar-width/status-string/arrow-direction/layout tests run headless. *(**partly superseded** — `arrow_quadrant()` was deleted: it returned a quadrant label instead of a vector, was never called by the renderer, and its tests only asserted the helper against itself. `planet_minimap_marker()` + `planet_arrow_points()` are the live path now.)*
- **Minimap scale** fits the *whole system* into the minimap's half-width: `scale = minimap_half / (system_pixel_size / 2)`. The ship sits at its world position and the planet anchors the map centre. If an entity's scaled position falls outside the minimap half-extent in either axis, it is "off-map" (`is_planet_off_map`) and gets a coloured marker (`PYRITE` for the planet, `STAR` for stars) at its scaled slot rather than a single direction arrow. *(**superseded** — the map is player-centred and off-map planets become a large arrow; see review fix 4.)*
- **Enemies, cargo, credits, and nav-selection are read from `HudView` attributes with empty/zero defaults** (e.g. `self.enemies`, `self.nav_selected_name`). They don't exist in `GameState` yet (Stages 7/9/10/11), so later stages populate these attributes rather than reaching into unrelated modules. Stage 6 only wires the ship-status bars, which *do* exist (`fuel`, `stats.shields`, `stats.armor`).
- **`GameState.off_map_positions`** is a new public dict (default `{}`) holding world-coordinate positions of entities pushed past the map edge, keyed by type. It is read read-only by the HUD minimap; later stages populate it instead of reaching into presentation code. *(**removed** — no stage ever wrote to it, and "the HUD asks the model for positions the HUD itself computes" is backwards coupling; see review fix 4.)*
- **Landing prompt** ("Press L to land here") is a pure helper `landing_prompt_text(game_state, planet_pos)` returning the message when within `landing_range`, drawn over the game-view rect by `TacticalView`. *(**superseded — it was never drawn**: the helper had callers only in tests. The live path is `TacticalView._update_landing_prompt()` → `MessageOverlay`; see review fix 5.)*
- **Ship status bars are horizontal and number-free.** Each row lays out a label then its bar side by side (spec: "labels on one row each, with a simple bar display next to each (no numbers)"). All three rows share the same left edge so every bar starts after the widest label ("shield"/"armor", 5 chars) and they all align. Rows are `LINE_HEIGHT` tall — not the old `BAR_HEIGHT` — so the ~18px label fits inside its own border box instead of overflowing it. Bars fill proportionally to `current / capacity`, using the new `max_shields`/`max_armor` capacities on `ShipStats`.
- **Navigation status got a taller box.** Its cached rect height was raised from `BAR_HEIGHT` (8px) to `LINE_HEIGHT` so the 2px border can actually enclose the "No destination" text, and the glyph is centered vertically inside. Same fix applies conceptually to the nearest-ship readout.
- **HUD text must render opaque.** ~~`SysFont(...).render()` returns an `SRCALPHA` surface whose glyphs carry low coverage alpha (~20/255); blitting that onto the game's non-alpha display surface alpha-blends it toward black, washing out every HUD glyph. All font renders now call `.convert()` (strips the alpha channel → opaque), and this was caught by a pixel-exact smoke test rather than remaining a visual surprise.~~ *(**wrong, and the cause of an ugly bug**: `.convert()` deletes the coverage, so every string blitted as a solid filled rectangle of its own colour. See "Manual-testing visual fixes" below.)*

## Stage 6 review fixes (post-review, before Stage 7)

A review of Stages 1-6 against `localhost-challenge-tweaked.md` found nine
"do-not-skip" defects in Stage 6. All nine are fixed here; the suite went from 95
to 143 tests. Each entry records *why*, because most of these were invisible to
the existing per-stage tests.

1. **The HUD is a component of `GameScene`, never a scene-stack entry.**
   `SceneManager` deliberately routes `handle_event()`/`update()` to the top scene
   only (Stage 2 decision), so pushing the input-free `HudView` above
   `TacticalView` starved the simulation: 60 frames of held Up+Left left the ship
   at `(0, 0)` with 1000 fuel and an empty input layer, while the suite stayed
   green. New `src/scenes/game_scene.py` composes `TacticalView` + `HudView`; the
   difficulty dialog now `replace()`s the title with `GameScene`, leaving exactly
   one scene on the stack. *Rejected alternative:* make `SceneManager` update every
   scene on the stack — that breaks the modal semantics the map/spaceport/game-over
   stages depend on (a modal must block gameplay input), and the stack order already
   expresses it.
2. **`main_loop` stopped knowing scene classes.** It had grown a
   `manager._stack[-1]` poke and an auto-push of `HudView`; a loop that imports
   scene types silently re-couples the layers. In its place:
   `FixedTimestepLoop.step_once(events=None, dt=FIXED_DT) -> bool` plus a thin
   `run()` that only owns the 60FPS clock. `step_once` is the seam the integration
   tests drive, so the wiring it exercises is the wiring that ships.
3. **One `GameState` per play session.** `GameScene` creates it from the selected
   config and hands the *same object* to the tactical view and the HUD;
   `HudView.__init__(manager, game_state)` raises on `None`. The HUD used to build
   its own `GameState`, so bars/minimap reported a phantom ship that never changed
   while the real one flew off.
4. **The HUD column is cleared, and so is every panel interior.** `HudView.draw()`
   fills `x >= VIEW_WIDTH` with the HUD background before drawing anything, and
   `_panel()` fills a component's box before stroking its 2px border, so the
   difficulty dialog's translucent panel can no longer bleed through permanently
   (observed: pixel `(690, 500)` read `(30, 30, 50)` forever; now `(0, 0, 0)`).
   Clearing the row boxes is also what makes a *shrinking* bar visible: without it,
   the previous (longer) fill survives the redraw and fuel/shield/armor read as
   permanently full. While in there: the border stroke used `rect.right`/`rect.bottom`
   instead of `right - 1`/`bottom - 1`, leaving the bottom and right edges unstroked.
5. **Minimap is player-centred, per spec.** White 2x2 ship fixed at the map centre,
   green 4x4 planet offset by `(planet - ship) * scale`, red 2x2 contacts, and a
   *large arrow* when the planet is off-map (`planet_minimap_marker()` chooses
   marker-vs-arrow, `planet_arrow_points()` builds the triangle). The previous
   planet-centred map drew the ship 3x3 near the centre, never showed the planet,
   and blitted "off-map" markers at their unscaled coordinates (one landed at
   x = 1405, i.e. off-screen). Off-map contacts are now culled. `arrow_quadrant()`
   and `GameState.off_map_positions` were deleted rather than kept as test-only
   helpers: a pure helper that the production path never calls is a second,
   unenforced implementation of the truth.
6. **The landing prompt actually appears.** `landing_prompt_text()` had test callers
   and no production caller. `TacticalView._update_landing_prompt()` now feeds it to
   a new `src/overlays.py::MessageOverlay` (sticky text + transient banners,
   de-duplicating, frame-budgeted, confined to the game-view rect). Stages 8/11 get
   the banner seam ("System boundary reached", payouts, etc.) instead of each
   inventing their own text drawing.
7. **Sprite rotation: degrees, and the right sign.** `pygame.transform.rotate` takes
   *degrees, counter-clockwise*; the code passed `math.radians(heading)`, so the
   sprite barely moved (`rotate(radians(90))` left the nose pointing east: nose
   centroid offset `(+14.5, -1.0)`). It is now `rotate(-heading)`, negated because
   the model's heading is clockwise-positive in a y-down screen space
   (`heading 0` = east, `heading 90` = south). Verified nose centroid offsets:
   0° `(+14.5, -0.5)`, 90° `(-0.5, +14.5)`, 180° `(-15.5, -0.5)`, 270° `(-0.5, -15.5)`.
   Related: held Left/Right were signed the wrong way (Left *increased* heading, i.e.
   turned clockwise). Left now decreases heading; the reverse-course flip still
   rotates in its original direction, so Stage 3's timing tests are unchanged.
8. **Starfield scrolls, camera follows the ship.** `TacticalView.update()` calls
   `starfield.update(vx, vy)` (it was never called, so the starfield was a static
   wallpaper), and `world_to_screen(world_x, world_y, ship_position, view_center)`
   pins the *ship* to the view centre, sliding the planet past it (spec: "the
   player's ship is always centered and zoom is fixed"; the planet must be
   something the player flies *to*). Stars stay in view space rather than being
   world-anchored: `Starfield`'s tested "shift by exactly delta" invariants are
   frame-relative, and world-anchoring them under a ship-locked camera would double
   the scroll. Star box half-extent is `max(VIEW_WIDTH, 768) / 2` so the taller axis
   is not star-free.
9. **The selected difficulty is honoured.** `SceneManager.game_config()` returns the
   flat dict for `selected_difficulty`, falling back to
   `DEFAULT_DIFFICULTY_CONFIG = "config_medium.json"` if a game somehow starts with no
   selection. Both the tactical view and `GameScene` use it; the previous literal
   `configs["config_easy.json"]` lookups made easy/medium/hard byte-identical in play.
10. **Integration tests exist.** `tests/test_game_flow.py` drives the real
    `FixedTimestepLoop.step_once()` with real posted pygame events: title →
    difficulty click → `GameScene` on a one-entry stack, hard-config values actually
    reaching the ship, thrust moving the ship and burning fuel, rotation/reverse
    through the whole pipeline, HUD column free of dialog residue, QUIT stopping the
    loop. Every other stage test calls `scene.update()`/`draw()` directly, which is
    exactly the hole the frozen-game regression fell through.

Small things fixed because leaving them would have re-broken the above:

- **`src/fonts.py`** caches `SysFont` (`game_font(size, bold)`) and centralises the
  `.convert()` requirement; `hud.py` was constructing a fresh `SysFont` on every
  render call (several per component per frame).
- **Ship sprite nose**: the rear wings were drawn at `3 * length / 4`, which is where
  the nose block begins, so the wings painted the nose out and every heading looked
  identical. Wings moved aft, nose drawn last (200 nose pixels now survive at every
  heading).
- Dead imports/pruned helpers in `main.py`, `hud.py`, `tactical_view.py`,
  `starfield.py`, and the stage tests.

Deliberately **not** fixed in this pass (each is a later stage's job or an open
design question, recorded so it does not get lost):

- **`GameState.boundary_reached_this_frame()` always returns `False`.**
  `_boundary_reached_this_frame` is initialised and never written. `on_boundary()`
  does work, and the spec wants no wall — it wants a message at most once every five
  seconds, which is Stage 8; whoever implements it must either drive that flag or
  delete the accessor rather than leave a stub that silently lies.
- **`rng.seed` from config is never applied.** Nothing calls `random.seed()`; and
  since the starfield now draws numbers from `GameState.rng` (one RNG per session, on
  purpose, for reproducibility), any future seeding must happen *before* the tactical
  view is constructed, or be re-applied per system in Stage 7 — seeding later changes
  the star layout too.
- **`stats.max_shields` / `max_armor` are captured from the config at construction.**
  The HUD reads capacity live, so Stage 12 upgrades must update the `max_*` fields or
  the bars will misreport; nothing enforces that coupling yet.
- **`economy.missions_min/max` in the shipped configs fall outside the spec's example
  range** (easy 6-10, hard 3-5 vs the spec sketch's 4-8). Plausible as a difficulty
  knob, but the pydantic schema has no numeric bounds at all, so no config range
  violation is currently detectable.
- **The accumulator drains at most one step per frame** (`if
  self._accumulator >= FIXED_DT: self._accumulator -= FIXED_DT`), so a frame slower
  than 1/60 s silently loses simulation time. The bounded accumulator is
  spec-mandated; the "never more than one step" part is an implementation choice that
  Stage 9+ (combat timing) may care about.
- README/docs pass and the remaining review backlog (fuel-sufficiency landing rule,
  system-boundary messaging) are untouched on purpose: one stage at a time.

## Manual-testing visual fixes (two glitches found by eye, not by the suite)

Both of these survived 152 green tests because the suite checked *which* strings
were rendered and *where*, but never what the pixels looked like between the
glyphs. A screenshot (dim overlay + solid text blocks) is worth several hundred
assertions here. Screenshot added to demonstrate problem: `stage6_screenshot.png`

- **All tactical/HUD text rendered as solid filled rectangles.** pygame's
  `Font.render(antialias=True)` returns an `SRCALPHA` surface in which **every
  pixel of the glyph box already carries the text colour** - measured on the
  shipped font: 1765 of 2178 pixels had `alpha == 0` and RGB `(140, 255, 140)` -
  coverage lives only in the alpha byte. The font helper called `.convert()`,
  which converts to the display format *and throws the alpha byte away*, so the
  whole bounding box blitted at full colour: banner, labels, and readouts each
  became an unreadable slab. Measured effect: `convert()` → 4800 banner-coloured
  pixels covering **100%** of the banner's bounding box; `convert_alpha()` → 87
  pixels, **3%**.
  `src/fonts.py::render_text` now uses `convert_alpha()` (fast display-format
  conversion, coverage preserved). The earlier "glyphs wash out toward black, use
  `.convert()`" decision recorded above was based on a misreading of antialiasing
  and is retracted.
- **A cancelled difficulty dialog stayed visible on the title screen.** The user's
  guess - "the title screen is not clearing" - was right in effect, wrong in
  mechanism: `TitleScene.draw()` *did* blit a full-window image every frame, but
  `resources/title_screen.png` was generated on a `SRCALPHA` surface with 3-tuple
  colours on a 4-pixel stride, so three of every four rows were fully transparent
  (2880 of 3840 sampled pixels had `alpha == 0`). A translucent background makes a
  "full-screen blit" into a *composite*: the dialog's panel `(30,30,50)`, its
  border `(100,100,140)`, and its dim overlay stayed stamped under the title
  (10266 dialog pixels measured inside the panel rect after cancelling), and the
  title glyphs re-composited over their own previous frames until they saturated
  to solid white. Three separate guards now exist, because any one of them can
  regress alone:
  1. `scripts/generate_title_screen.py` draws every scanline onto an **opaque**
     surface, and the asset was regenerated.
  2. `TitleScene.on_enter` normalises whatever asset it loads to an opaque surface
     (composited onto the clear colour once at load), so a bad asset can never leak
     through the per-frame blit.
  3. `TitleScene.draw()` fills the window with `_CLEAR_COLOR` before drawing - a
     full-window scene owns the whole window and must repaint, not composite.
- **Test-stride gotcha worth remembering** (this one bit the regression test
  itself): sampling `get_at` on a stride-2 grid makes a *100% filled* box measure
  as 25% coverage. `tests/test_game_flow.py::test_tactical_text_is_readable_glyphs_not_solid_blocks`
  therefore does a coarse pass to find the banner's bounding box and then scans
  that box pixel-by-pixel; with the bug it reports 100%, without it 3%.

## Stage 7 — System graph + map view + fog of war

An interrupted first revision of Stage 7 was reviewed rather than discarded: the
graph generator and the selection/fog rules were sound, so they were kept and
finished. Everything below marked **(fixed)** was broken in that revision and is
now covered by a test. The stage gate grew from 155 to 231 tests
(`tests/test_stage7.py`, 72 tests, plus 5 `map`-section config tests).

- **The `map` config section is `{system_count, connections_min, connections_max,
  alpha_connections}`**, added to the schema (`_MapConfig`), to `base_config()`
  (hence to the `config-factory` fixture) and to all three shipped files in the
  same change. The first revision added the JSON keys *without* the schema: with
  `extra="forbid"` the shipped configs stopped validating and the fixture configs
  lacked the section, so 19 tests failed and `GameScene.__init__` died on
  `KeyError: 'map'` — i.e. the game did not start at all. This is the dev plan's
  "unrecognized config keys are fatal" trap, sprung exactly as warned.
- **Cross-field validation for `map` lives in the config schema, and the generator
  still validates its own output.** Impossible ranges (`connections_min` >
  `connections_max`, `system_count: 27`) are rejected at startup with the key
  named, because a config the loader accepts but the generator cannot build would
  otherwise fail mid-session at "New game". `GraphConstraints.check()` duplicates
  a little of that on purpose: the generator must be usable without the loader
  (tests, tooling, a future save-game path).
- **The 26 system names stay in code** (`NATO_SYSTEMS`), per the spec's rule that
  enum-like IDs do not belong in config. Only their *count* and their connections
  are configurable. **(fixed)** The roster contained "Kiwi" — that is not a NATO
  word; it is "Kilo". "Juliett" (two t's) and "Xray" (one word) are kept because
  they are the NATO spellings, and that looks like a typo, so it is written down.
- **Topology invariants are checked against a `GraphConstraints` value object, not
  hard-coded constants.** **(fixed)** `SystemGraph.validate()` previously asserted
  "26 systems, degree 1..3, Alpha→Bravo/Charlie/Delta" as literals while the
  generator accepted `system_count`/`connections_*` from config, so the knobs were
  decorative and any change to them crashed the game (`ValueError: Alpha must
  connect to Bravo, Charlie and Delta` for `connections_max: 2`). Now the
  generator and the checker are held to the same object, and the property tests
  assert against the constraints they generated with.
- **`connections_min` is enforced by a third generation phase** that gives every
  under-connected system an extra lane, and raises `GraphGenerationError` when the
  request is unsatisfiable (e.g. `min=max=3` over 5 systems: an odd degree sum
  cannot exist). The first revision stored `connections_min` and never used it.
  Consequence worth knowing: with the shipped `connections_min: 1`, a 26-system
  world has exactly 25 edges — a **spanning tree with no route redundancy**, so
  there is exactly one route back to Alpha. That satisfies the spec's "degree ∈
  [1,3]" and is left as the shipped default; raising the min to 2 in config is the
  knob for a world with alternative routes (and is tested).
- **Every RNG draw in the generator comes from a list in `NATO_SYSTEMS` order,
  never from set or dict iteration order.** **(fixed — this is the nastiest bug in
  the revision)** Phase 2 picked an attachment source out of a `set`, and Python
  randomises string hashing per process, so the *same seed produced a different
  world in every run* (three runs of seed 42, three different graphs). Invisible
  inside one pytest process; fatal for replaying a saved world. Regression test:
  `test_generate_withTheSameSeedAcrossHashSeeds_shouldProduceIdenticalAdjacency`
  generates the graph in three child processes with different `PYTHONHASHSEED`
  values and compares digests.
- **The world (graph *and* layout) is owned by `GameScene`/`SystemMapState`, not by
  the map screen.** `SystemMapState` holds the immutable `SystemGraph`, the
  immutable `MapLayout`, and the mutable fog/selection state, and exposes
  `visible_nodes()` / `visible_edges()`. The view draws exactly what it is told.
  *Rejected alternative:* let `MapView` compute its own node ring and re-derive
  visibility in a nested loop over all 26 systems — that is what the first
  revision did, and it both re-laid-out the world on every modal open (spec:
  "layout computed once per game and cached") and drew all 26 node circles
  regardless of reveal state, so the entire map was visible on turn one. The test
  `test_openingAndClosingTheMap_shouldNeverRegenerateTheWorld` counts
  `build_map_layout` calls; `test_draw_withUnrevealedSystems_shouldNotPaintTheirCircles`
  counts pixels.
- **`MapLayout` carries the geometry the renderer *and* the click test use**
  (positions, label anchors, measured label sizes, derived label boxes, hit
  radius). One rectangle per label, agreed on by both sides, so a label you can
  see is a label you can click.
- **Placement is one evenly-spaced ring, ordered by depth-first preorder from
  Alpha.** A degree-≤3 tree placed this way puts each subtree in one contiguous
  arc, so edges drawn as chords never cross — measured at **0 crossing pairs per
  world across 40 seeds**, versus ~59 with the alphabetical ordering the first
  revision used. The placement math is unchanged from `circular_positions`, so it
  stays trivially testable.
- **Labels sit radially outside their node, each at its own offset, and the offset
  is solved per angle.** "Half the label height plus a gap" is the intuitive rule
  and it is wrong everywhere except 12 and 6 o'clock: a 64×14 label at the 3
  o'clock slot reaches 32 px back towards its own node, so a 24 px circle 18 px
  away is *inside* the label's bounding box. `label_offset_for_angle()` bisects on
  the true point-to-box distance.
- **The label font size is the largest that verifiably fits, and the bound is
  worst-case over *any* ring ordering.** Two guards, both needed:
  `overlapping_pairs()` on the layout that was built (necessary) and
  `_labels_clear_adjacent_slots()` requiring the two widest names to fit side by
  side at the tightest point of the ring (sufficient for every world). Without
  the second guard, verifying only the built layout accepted 20 pt for some seeds
  and 14 pt for others — the map's typography would have drifted from world to
  world.
- **Overlap checks use the geometry things are actually drawn with**: label/label
  is box-vs-box, node/node is circle-vs-circle, label/node is circle-vs-box. A
  bounding-square test for the circles demands clearance no 1024×768 window can
  afford (it pushes the label ring off screen), and it also produced 3200 false
  positives while being written.
- **`HEADER_BAND` (72 px) is part of the layout contract**, so the modal's own
  copy (banner, `Current: X  Destination: Y`, hint line) can never collide with a
  system label: `fits_on_screen()` treats the band as a hard edge. Without it the
  ring's topmost label lands at y≈16, straight through the header text.
- **`MapLayoutError` is raised when no font size fits** (e.g. a 120×120 window).
  A silently cramped map is worse than a named failure.
- **Hit testing lives in the layout** (`MapLayout.node_at`): a click counts if it
  lands in a node's hit circle *or* in that node's label box, and only
  *revealed* systems are candidates — so fog of war is enforced at the pick level,
  not only in the renderer. The hit radius is 45% of the node-to-node gap, so two
  nodes can never both claim one click.
- **Toggle-off is tested before selectability in `handle_map_click`.** **(fixed)**
  An already-selected system is still a perfectly legal selection target, so
  `can_select` first re-selected it forever and the spec's toggle-off was
  unreachable code. Every rule passed in isolation; only a two-click test sees it.
- **`SystemMapState` refuses a `MapLayout` from a different world** by comparing
  the layout's placement order with a recomputed preorder of its graph. Two
  worlds contain the same 26 names, so a name-set comparison passes while the
  coordinates belong to another topology — every click would select the wrong
  system with nothing visibly wrong.
- **A full-window scene repaints the whole window.** `MapView.draw()` fills the
  surface before drawing (same rule as `TitleScene` in the manual-fixes section).
  **(fixed)** The first revision never cleared, so the tactical view, HUD and
  minimap showed straight through the "modal". Regression test paints the canvas
  magenta and asserts zero magenta pixels survive (exact aligned scan, because the
  stride-2 sampling gotcha in the manual-fixes section makes coverage counts lie).
- **Each label gets a background-coloured halo before its glyphs are blitted.**
  With the shipped tree graph, DFS placement keeps every edge out of every label
  box (measured: 0 intersections across 25 worlds), but a config that raises
  `connections_min` adds cycle edges that would cut a strikethrough through a
  name. One rect is cheaper than auditing every future edge for it.
- **The current system is drawn green and the map prints a header line.** The spec
  asks for "white circles + labels + thin grey edges"; a map with no "you are here"
  marker and no destination readout is unusable, so the additions are recorded
  here rather than smuggled in. Selection still uses the spec's `[ ]` brackets
  (rendered as real glyph brackets hugging the label box, not hand-placed rects).
- **`J` is not Stage 7's business.** The map sets a destination and the HUD nav
  line reflects it (`No destination` → `Hyperspace / Bravo`, the Stage 6 seam), but
  `J` still does nothing until Stage 8 builds the jump animation. The header hint
  mentions J; a player who presses it gets nothing, which is expected for this
  stage.
- **Two jump flags, deliberately separate.** `GameState.is_jumping`
  (`begin_jump`/`end_jump`) is model state the map gate consults;
  `InputLayer.locked` suppresses controls. The map gate needs a *queryable* state
  that survives an input drain, and Stage 8 owns setting both. Recorded because
  they look duplicative.
- **The simulation is paused while the map is open** — `SceneManager` routes
  `update()` to the top scene only (Stage 6 review fix 1). That is the modal
  semantic the stack exists for; `test_simulationStaysFrozenWhileTheMapIsOpen`
  pins it so a future "update every scene" change cannot quietly make the map a
  real-time overlay.
- **`MapView(state)` takes only the map state; the manager arrives via
  `on_enter`.** **(fixed)** The first revision's signature was
  `MapView(manager, state)` but `GameScene` passed *itself*, and `on_enter` then
  overwrote the attribute — so `self._manager.pop()`, `.quit()` and `.audio` were
  being called on a `GameScene` that has none of them, and only the accidental
  overwrite kept it working. Related cleanups: `GameScene` no longer reaches into
  `manager._stack` (only the top scene is updated, so a "map already open" guard
  is dead code), the bogus "avoid a circular import" local re-import is gone, and
  `TacticalView.update()` / `GameScene.update()` now return typed actions.
- **`GameScene.draw()` syncs `hud.nav_selected_name` from the map state** rather
  than doing it in `update()`: `update()` does not run while a modal is on top,
  but `draw()` always does, so a destination chosen on the map would otherwise
  only appear on the HUD after closing it. Mutating in `draw()` is a small smell;
  the alternative (the HUD reaching into the map state) is worse coupling.
- **`tests/test_zz.py` was deleted**: a leftover Stage 6 debug probe
  (`test_debug_colors`, printing sampled colours), not a Stage 7 test.
- **connections_min** ships with default **2**, not 1. The spec calls for
  each node to have a minimum of 1 connection, but this can lead to more
  tedious exploration (have to traverse back to Alpha to explore another branch).
  Shipping with default of 2 in all three configs makes inter-system jumping easier.
- **Gotchas for the next stage.** (1) The graph is seeded from a *separate*
  `random.Random(config["rng"]["seed"])` — a world seed — while `GameState.rng` is
  still unseeded; `rng.seed` does not yet reproduce a whole playthrough, only the
  world. Stage 9/10 RNG work should decide whether to thread one generator
  through. (2) Layout geometry is baked for the non-resizable 1024×768 window; if
  resizing ever lands, the layout must be rebuilt on resize. (3) With `min=1` the
  ring's DFS ordering still draws a few long "spoke" edges across the middle of
  the map: correct, uncrossed, but visually busy — a radial/tree layout is the
  upgrade path if that ever bothers a human.

## Stage 8 — Jumping (hyperspace)

- **The jump is a three-phase sequence, and the arrival happens inside a white-out.**
  The spec asks only for "the player's craft accelerating greatly in the facing
  direction for three seconds". The arrival was therefore given a second phase:
  `tactical.jump.frames` (180) frames of uncapped burn, then
  `tactical.jump.transition_frames` of screen flash during which the world is
  swapped. This is a **deliberate deviation, and it is load-bearing rather than
  decorative**: the swap (new system, new starfield, ship teleported 400-850 px,
  velocity zeroed, shields refilled) is a discontinuity, and a discontinuity
  under a fully opaque white screen is invisible. Without it the player watches
  the universe teleport. `blind_frames_for()` is the single source of timing
  truth: the model swaps the world on exactly the frame `flash_alpha()` reaches
  255, and `test_advance_shouldSwapTheWorldOnTheFrameTheFlashTurnsFullyOpaque`
  pins both sides of that seam.
  *Rejected alternatives:* cutting straight from burn to arrival (what the spec
  literally says — reads as a glitch, and the old system's departure is jarring);
  a fade-to-black (slower, and the arrival then fades *in* over the old system);
  a wipe/shockwave alone (the shockwave is kept, but only on the way out of the
  flash, where it is actually visible).
- **The flash covers the whole window, HUD included; the shockwave starts at the ship.**
  `GameScene` draws the flash *after* the HUD, because a flash that politely
  skipped the right-hand third reads as a rendering bug. `FlashOverlay` therefore
  takes a `region` (what gets whited out) and an `origin` (where the boom starts):
  the game-view centre, not the window centre. Ringing the empty middle of the
  window is how you tell a player an effect was pasted on rather than caused.
- **`transition_frames` is config, and it differs by difficulty** (easy 36,
  medium 45, hard 60). It is presentation, but it is also the only part of a jump
  during which the player is helpless, so making it a knob is honest — and
  Stage 14's "no hard-coding" sweep gets one more number that demonstrably moves.
- **`spawn_distance` is a config band, validated against two other keys.**
  `tactical.jump.spawn_distance: [min, max]` (world px from the planet). The
  loader rejects a band that starts at or inside `tactical.landing_range` (the
  player must fly to the planet, per spec) or that ends beyond
  `tactical.system_pixel_size / 2` (arriving outside the system you just paid to
  reach). Both cross-field checks live in `_TacticalConfig`, because
  `_JumpConfig` cannot see the other two keys. Bearing is uniform over the whole
  compass; distance is uniform in the band (so outer rings are sparser per unit
  area — the constraint the config expresses is a distance band, not an area).
- **The burn is counted by the model, not by the jump sequence.** **(fixed)**
  The first cut counted burn frames in `JumpController`, which silently delivered
  **179** frames of a "180 frame" animation: the fixed timestep on which `J` is
  drained has *already* called `advance_frame()` before the scene sees the action,
  so the request frame is not a burn frame. `GameState` now counts its own
  integrated hyperspace frames (`jump_frames`) and the controller only supplies
  the target. Visible symptom of the bug: terminal speed off by one increment of
  the jump acceleration; invisible in play, fatal for the "frame-exact" gate.
- **A phase's first frame is the frame it begins on** (`_frames_elapsed = 1` in
  `_enter_phase`). The flash and the transition phase must advance in lockstep,
  and `GameScene._advance_jump()` ticks the flash *before* the controller for the
  same reason. Consequence, stated so it does not look like an off-by-one: the
  whole sequence takes `frames + transition_frames - 1` pumped timesteps after the
  request, and `frames + transition_frames` counting the frame `J` was pressed on.
- **Two jump locks, deliberately separate** (Stage 7 flagged this). `GameState.is_jumping`
  is the queryable model state (the map gate reads it, the boundary clamp skips it);
  `InputLayer.locked` suppresses controls and drains queued edges. Stage 8 sets
  both: lock on the accepted request, unlock on `EVENT_JUMP_ENDED`.
- **`begin_jump()` clears the latched control frame** (and `end_jump()` does again
  for symmetry). The input layer is locked during a jump, so a thrust key held
  when `J` landed used to keep feeding ordinary *capped* thrust into the jump: the
  ship then accelerated at the wrong rate for all 180 frames. In the real loop the
  effect is invisible (both burns point along the heading); the terminal-speed test
  is what catches it.
- **Boundary clamping lands in Stage 8**, because the spec's jump exemption is
  meaningless without the wall: the ship is pinned to
  `±system_pixel_size / 2` and the *velocity component through the wall* is zeroed.
  *Rejected alternative:* clamp position only and keep velocity — the ship then
  accumulates a decade of outward drift while pinned against an edge and
  slingshots away the moment it turns around. The spec's rule ("cannot move any
  further in that direction", thrust and fuel burn still allowed) is positional;
  zeroing the normal component is what makes that behave.
  `boundary_reached_this_frame` is set only on frames where a clamp actually moved
  something, so a ship drifting parallel to an edge is not "in contact" for banner
  purposes.
- **The boundary banner's repeat policy is config**: `tactical.boundary_warnings`
  `{message_frames: 120, cooldown_frames: 300}`. The spec's "at most once every
  five seconds" is the cooldown; "briefly" is the message duration. `MessageOverlay`
  deliberately owns no repeat policy (Stage 6 decision), so the cooldown lives in
  `TacticalView._update_boundary_warning()`.
- **The exact-fuel game over is a seam, not an implementation.** Spec: `J` with
  *exactly* the jump's fuel cost is an immediate game over. Stage 13 owns the
  game-over screen, so Stage 8 guarantees only what it can see: no jump, no fuel
  spent, and `GameScene.pending_game_over = True` for Stage 13 to consume. Two
  tests pin it, including the ordering trap below.
- **Blocker check order is load-bearing: the fuel checks come last.** The
  exact-fuel rule is a death sentence, so it must never fire for a jump that was
  already illegal for an innocent reason. A player nudging the planet with exactly
  250 fuel must be told about the planet. Order: already jumping → no destination
  → destination not adjacent → inside landing range → insufficient fuel → exact
  fuel. `test_request_withExactlyTheJumpCost_butInsideLandingRange_shouldReportThePlanetNotTheFuel`
  is the only thing standing between a future refactor and a murderous one.
- **"No system selected" is silent.** The spec says `J` "does nothing" in that
  case, so no banner. The blockers that carry copy are the two a player can cause
  and be confused by (`insufficient fuel`, `Cannot jump this close to the planet`);
  `already_jumping` and `invalid_destination` are unreachable through legal play.
- **Selection is cleared on arrival, not on request**, so the HUD's nav line keeps
  reading `Hyperspace / Bravo` for the whole three-second burn and only then falls
  back to `No destination`. The spec only requires that no selection survives a
  jump; showing the destination during the animation is the difference between a
  dashboard and a blank one.
- **Arrival regenerates the starfield and repaints the planet per system.** A jump
  that kept the old sky would show the player flying *back* into the system they
  just fled at 200 px/frame and stopping dead. 150-star invariant holds (the same
  `Starfield` contract, new draws from `GameState.rng`). Planet colour is now
  `planet_color_for(system_name)` via `zlib.crc32`, not the planet's diameter:
  **`hash()` must not be used here** — Python randomises string hashing per
  process, so every planet would repaint every launch and no test could assert on
  it. Same trap as Stage 7's `PYTHONHASHSEED` note, different module.
- **`JumpController` owns policy, `GameState` owns mechanism.** The controller
  decides *whether* (rules), *how long* (phases), and *what happens on arrival*
  (reveal, spawn, refill); `GameState` provides uncapped thrust
  (`set_jump_acceleration`, including cutting it to 0 for the white-out) and the
  boundary exemption. The burn's acceleration is never read from
  `player_ship.acceleration_rate`, so a jump can exceed `top_speed` without
  touching the normal flight model — Stage 3's "60 frames of thrust reaches
  exactly 5.0" tests are untouched.
- **The white-out freezes the burn but does not zero velocity.** The ship coasts
  through the flash at its terminal jump speed (~216 px/frame) and *then* arrives
  stopped. Cutting the burn is the sequence's business; killing velocity during
  flight would contradict the Newtonian model for no visible reason (the screen is
  white). `arrive_in_system()` is deliberately one call bundling
  spawn + velocity reset + shield refill: a jump that reset the position but kept
  hyperspace velocity would fling the player back out of the system they paid for.
- **Audio: two new generated buffers, built lazily, gains in code for now.**
  `play_jump_spinup()` (exponential frequency ramp 130→1150 Hz — exponential
  because equal time spans must cover equal musical intervals, a linear ramp sounds
  like a siren) and `play_thunderclap()` (crack of low-passed noise + 46 Hz rumble,
  fast attack / exponential tail). Generated on first use, not at construction:
  ~150k samples of pure Python maths would cost the title screen half a second for
  a sound many runs never trigger. Thunderclap noise uses a fixed-seed `Random`, so
  the buffer is byte-identical per run and *can* be digest-pinned. Gains stay in
  code (`_JUMP_SPINUP_GAIN`, `_THUNDERCLAP_GAIN`) matching Stage 2's confirm beep;
  **Stage 12 owns moving every gain into config** — it is the dedicated audio pass,
  and adding a half-populated `audio` section now would collide with it.
- **Hyperspace presentation: warp tunnel + smeared stars, view-space.** `WarpTunnel`
  streaks grow *multiplicatively* (`radius *= 1 + speed(intensity)`) because
  accelerating outward is the perspective cue that the camera is moving *into* a
  tunnel rather than sliding across one; count is invariant like the starfield's,
  and `reset()` re-seeds near the vanishing point on arrival. Ordinary stars are
  drawn as smears along the velocity vector, capped at `_MAX_STAR_STREAK` (180 px) —
  an uncapped smear at 216 px/frame is a solid white rectangle. Streak culling pads
  by that cap, not by the view edge, or a smear that starts off-screen and crosses
  the view gets culled away.
- **`TacticalView` hides the ship only while the flash is opaque**
  (`JumpPresentation.ship_visible` is false for the first `BLIND_FRACTION` of the
  transition, true for the fade). Leaving it on screen is the giveaway that the
  arrival is a teleport rather than a journey. Hiding it for the *whole* white-out
  was the same bug wearing a different hat: the ship then popped into existence on
  the last frame. The fade is the arrival being revealed, and the player is part of
  that arrival. The ship is also *not* drawn between the flash and the shockwave
  during the burn: warp streaks paint over it deliberately.
- **The real-loop tests pin the world seed, and one guard test says why.** Those
  tests say `select("Bravo")` rather than "select some neighbour of Alpha", because
  a fixed expectation reads better than a computed one — but which systems are
  neighbours is a property of the graph generator. With `rng.seed: null` (the
  shipped default) every run drew a different map and those tests were ticking over
  on luck. `WORLD_SEED = 4242` in `tests/test_stage8.py` plus
  `test_thePinnedWorldSeed_shouldOfferEveryHopTheIntegrationTestsTake` turns that
  luck into a checked assumption that fails in one place, by name.
- **Fixture trap, worth knowing before Stage 9 writes more config tests:**
  `config_factory` *rewrites the three temp config files every time it is called*.
  A pre-call such as `config_factory(overrides={"rng.seed": 505})` followed by a
  helper that calls `config_factory()` again silently loses the override — three
  Stage 8 tests were configured that way and were running unseeded. Pass overrides
  through the helper, once.
- **`stage8_jump_sequence.png` is committed at the project root** (see
  `stage6_screenshot.png` for the precedent), generated by
  `scripts/capture_jump_frames.py --sheet`. An animation is the one part of this
  stage no assertion can vouch for; a contact sheet is reviewable in a way a
  300-line pixel test is not.
- **Jump presentation syncs in `update()`; the HUD nav line syncs in `draw()`.** Each
  seam syncs where its state changes. `update()` is the only thing that advances a
  jump, and `TacticalView.update()` *consumes* the presentation (warp intensity), so
  syncing at draw time left every consumer a frame stale. The nav line is the
  opposite case: it changes while `update()` is frozen under the map modal, so only
  a draw-time sync makes a destination chosen on the map appear immediately.
  Test consequence, documented in the test: `hud.nav_selected_name` assertions must
  call `draw()` first.
- **Not implemented in Stage 8, by design, with named owners:** NPC despawn on jump
  (Stage 10 — hook is `EVENT_ARRIVED`, already noted at the call site), the
  game-over transition for the exact-fuel case (Stage 13 —
  `GameScene.pending_game_over`), damage during the jump (Stage 11 — no immunity is
  granted anywhere in this stage, per spec), and the config-driven audio gains
  (Stage 12).
- **Gotchas for the next stages.** (1) `GameState.jump_frames` is reset by
  `begin_jump()` and is meaningless once `is_jumping` is false — Stage 13's
  stranded-fuel rule must read the fuel, not the frame count. (2) `pending_game_over`
  is a *latch*, not an event: Stage 13 must clear it when it shows the game-over
  screen, or the player dies again next frame. (3) The starfield now consumes
  `GameState.rng` draws on every arrival, so the arrival spawn draw lands at a
  different point in the sequence than a naive reading of "one draw per jump"
  suggests — relevant to Stage 9/10 determinism tests (ship spawn chance per
  system is seeded by system index, so keep it off this stream or thread a
  separate RNG, per the Stage 7 note). (4) `FlashOverlay.advance()` is only ticked
  while `GameScene` is the top scene; if Stage 13 lets a modal open during the
  white-out, the flash will hang mid-frame.

## Stage 9 — Spaceport + economy (the vertical slice)

- **The credit floor is *strictly above* zero: a purchase that would leave exactly
  0 credits is refused.** `CREDIT_FLOOR = 0.0` and `can_afford` is
  `credits - cost > CREDIT_FLOOR`. This is the same philosophy as Stage 8's
  "J with exactly the fuel cost is refused" rule: the boundary is a refusal with a
  message, not a cliff the player discovers by arriving with nothing. It also makes
  the spec's gate ("no purchase path producing credits ≤ 0") a *one-line* proof
  instead of an audit of six call sites, and it is asserted directly:
  `test_everyPortPurchasePath_withTheShippedConfigs_shouldNeverTakeCreditsToZeroOrBelow`
  drives accept/refuel/repair/upgrade against all three shipped configs.
  *Rejected alternatives:* allow 0 and treat it as broke (then Stage 13 must decide
  whether broke is a loss condition, which is Stage 13's call, not Stage 9's); a
  configurable floor key (a knob nobody asked for, and the spec's game-over rule
  already reads the balance).
- **Offer payloads are capped by the player's own hull, not by a constant.**
  `OFFER_CARGO_CEILING = 15` / `OFFER_PASSENGER_CEILING = 5` are ceilings, and the
  generator takes `min(ceiling, stats.cargo_room)` and
  `min(ceiling, stats.passenger_space)`. On hard the hull is 15 cargo / 4
  passengers, so the old constant ceiling produced offers that could *never* be
  accepted — an unclickable tease on a screen that is all about clicking. The
  invariant "no offer is permanently dead" is swept over 200 seeds.
- **One result type for everything a port sells: `PortTransaction(succeeded, reason,
  credits_spent)`.** The first cut had `LoadResult` and `PurchaseResult`, identical
  except for their names, and the spaceport promptly crashed with
  `AttributeError: 'LoadResult' object has no attribute 'completed'` because a
  handler guessed at the other type's field. Accepting a job, buying fuel, patching
  armour and buying an upgrade are the same transaction shape: did it happen, why
  not, and what did it cost. The view calls `_report(result)` for all four, so a new
  service cannot forget to show its refusal.
- **Fares are settled once and only once, by the model, on landing.** A `Mission`
  carries `offer_id = (visit_serial, index)`. `visit_serial` comes from
  `GameState.begin_port_visit()` — the model owns the numbering, so a board from a
  previous visit can never collide with the current one, and "accept the same job
  twice" (a money glitch the first cut allowed) is refused by identity rather than by
  hoping the view disables the button. `land()` unloads only the loads bound for that
  system, credits each fare exactly once, and returns a `LandingReport` — which is
  also the copy source for the "Unloaded 3 cargo units and 1 passenger at Bravo:
  +4,321 credits." message. Re-landing at the same system with the same job aboard
  pays 0, and that is asserted twice (model level and in the playthrough).
- **`land()` raises while a jump is in progress** rather than returning an empty
  report. Landing mid-flight would settle fares the player has not arrived to
  collect, and would be invisible; a `ValueError` at the seam is a bug the tests can
  find. `GameScene` cannot reach it (the modal owns the keyboard, and `_open_spaceport`
  refuses while jumping), which is exactly why an explicit guard is cheaper than a
  comment saying "can't happen".
- **`SystemGraph.jump_distance()` was added to the Stage 7 map layer.** The far bonus
  needs the *lane length*, which is a property of the world graph and not of the
  player's charts — a destination can be offered before it is revealed, so the fare
  must not depend on fog of war. Putting a BFS in the economy would have duplicated
  the graph's own adjacency rules; the method lives next to them and the economy
  calls it. Symmetry, finiteness, and "never exceeds the world" are swept over 200
  seeds, and a disconnected graph is a `ValueError` from the offer generator rather
  than a silently unpriceable trip.
- **Landed = immune, plus a grace window on launch.** `immune_to_damage` is
  `is_landed or launch_immunity_frames_left > 0`, armed by `launch()`
  (`tactical.launch_immunity_frames`, 120 frames = 2 s at 60 FPS). Two details worth
  knowing: `launch()` is idempotent, so a second launch does **not** re-arm the clock
  (otherwise parking and unparking indefinitely makes the ship invulnerable); and the
  immunity clock ticks through a jump, because it is a wall-clock grace period, not a
  "frames since you last stood still" counter. `advance_frame()` early-returns while
  landed, so the sim underneath the modal cannot drift the ship out of the port it is
  standing in.
- **`ESC` launches.** The spec names only the "Launch!" button. The README has
  promised since Stage 2 that `ESC` closes whatever modal is open, and a modal where
  `ESC` does nothing reads as a swallowed keyboard. `SpaceportView.handle_event`
  treats it as exactly equivalent to clicking Launch (same `launch()` order, same
  confirm beep).
- **(fixed) `InputLayer.reset_held_state()` exists because modals eat the `KEYUP`.**
  The `L` press is delivered to the tactical layer, which pushes the modal in the same
  frame; the release then arrives at the *modal*, which never forwards it. The input
  layer kept believing `L` was held, so the next press produced no rising edge —
  "the spaceport only opens every other time". `GameScene._release_finished_port_visit()`
  calls `reset_held_state()` when the visit is dropped. **Any future modal that can
  be opened by a bound gameplay key must do the same** (Stage 11's `T` scan and
  Stage 13's pause will).
- **`GameScene._open_spaceport()` refuses when a visit is already open.** In play the
  scene stack already guarantees this; the guard is there because "the stack protects
  me" is a property of the caller, and a re-routed key press would otherwise stack a
  second modal and re-roll the board the player is reading.
- **The spaceport screen is fixed geometry, and the capacities are computed from it.**
  `contracts_capacity()` = 10 rows, `upgrades_capacity()` = 7 (one per stat, and
  seven stats exist), `manifest_capacity()` = 4 lines. The services block is placed
  below the *worst case* of the upgrade list rather than chasing however many rows
  appeared this visit — the first layout did the latter, and the manifest promptly
  painted over the message line (`MESSAGE_RECT` at y=654 vs a fifth manifest line
  ending at 654). If a config ever raises `economy.missions_max` past the box, the
  board truncates with an honest "...and N more this port cannot show" note instead
  of rows running under the Launch button. One colour table (`PortPalette`), because
  two hand-maintained dicts of the same colours is how a disabled border stops
  matching a disabled caption.
- **Buttons are created once per visit, then synced — never recreated.** Rebuilding
  the board after every transaction moves widgets under the cursor mid-click.
  `_sync_buttons()` re-reads the model instead: `offer_is_accepted` → "Aboard"
  (disabled), level already bought → "Done" (disabled), `can_afford(offer.cost)` →
  grey the price out, and the service captions carry their own live price
  ("Refuel +12 units - 24 cr"). The affordability test is the model's own
  `can_afford`, so a caption cannot promise something the refusal text then denies.
- **Lore lives in `resources/lore.txt` (100 entries) and gets its own RNG stream.**
  The world graph, the gameplay, and the lore each draw from a separate
  `random.Random`, so adding a lore line cannot perturb ship placement — the Stage 7
  note about not sharing streams, applied. Entries may carry a `(System)` tag
  (substituted with the system's name; untagged entries are used verbatim); 100
  entries over 26 systems means a fresh-looking book per run without repeats inside
  one world. A missing or empty lore file is a **fatal startup error** (`SystemExit(1)`),
  consistent with the project's config policy: a game that silently boots with no
  spaceport flavour is a game with a broken feature nobody noticed.
  `LoreBook.for_world()` resolves `LORE_FILE` at *call* time, which is what lets the
  missing-file test monkeypatch the path at all.
- **Upgrade offers sample only upgradable stats, and the wall is per-stat.**
  `upgrade_max_level` (5) is enforced by the generator (a stat at the wall is never
  offered) *and* by `purchase_upgrade` (which recomputes the price from the config
  curve and refuses a stale level), so a screen holding an old board cannot be talked
  into a second level at the old price. Cost stays `base * multiplier ** (level - 1)`
  — exponential, exactly as Stage 7 decided; the table test pins level 1 = base price
  and level 5 = `2500 * 3**4 = 202500` on hard. `upgrade_steps` on the model is keyed
  by **stat name** (`weapons`), not by config key (`weapon_damage`); the mapping lives
  in one function, `upgrade_step_for()`.
- **No config keys were added by this stage — validation was.** All of the
  `economy.*`, `new_game.starting_credits`, `tactical.launch_immunity_frames` and
  upgrade-step keys this stage needs shipped in the Stage 7/8 config commits. What
  was missing was *checks*: fare ranges must be ordered and positive, upgrade
  multiplier ≥ 1.0 and max level ≥ 1, cargo/passenger room must be able to hold at
  least one job (a hull of 0 makes every offer dead), and the launch grace period must
  exist. Those live in `_EconomyConfig`, `_UpgradeStepConfig`, `_PlayerShipConfig` and
  `_TacticalConfig`, and load failure is fatal — the project's standing rule.
- **Deviation, worth flagging for Stage 14's sweep: the spec says "4–8 generated
  offers"; the shipped configs say easy 6–10, medium 4–8, hard 3–5.** The ranges were
  config data before this stage existed, and the difficulty-tuned spread is
  defensible (hard gives fewer, smaller offers on a smaller hull); the medium table
  matches the spec exactly. Recorded here rather than silently "fixed", because
  changing committed config data is a balance decision, not an implementation one.
  `missions_min`/`missions_max` are asserted to be respected over 200 seeds, so the
  range is a tested property either way.
- **Refuel and repair are "fill to full" buttons, not quantity pickers.**
  `buy_fuel(units=None)` and `repair_armor(points=None)` take an optional quantity
  (and are tested at partial quantities), but the screen offers one button whose
  caption is the live price of the whole fill. A slider was not going to fit the row
  grid, and the interesting part of the decision is the price, which the caption
  states. A full tank / intact hull renders "Full" / "Intact" and disables the button,
  so the screen never shows a 0-credit purchase.
- **Test determinism gotcha, learned the hard way: `base_config()` ships
  `rng.seed: null`.** Every scene-level Stage 9 helper therefore built an *unseeded*
  game — different world, different contract board, different first Accept button on
  every run. One test failed roughly one run in three because the job it happened to
  click was a passenger run and the assertion was about cargo. `SCENE_SEED = 4242` +
  `scene_config()` in `tests/test_stage9.py` fixes the seed for the whole file. If a
  future stage writes scene tests against `base_config()` directly, they are flaky by
  construction.
- **Two real-loop gotchas, both already paid for once.** (1) A `KEYDOWN` and its
  `KEYUP` posted in the same batch read as "key never pressed" — the press and the
  release must be pumped in *separate* frames (Stage 8's `_press` already knew this;
  Stage 9's `_tap_key` re-learned it). (2) A 4-hop lane cannot be flown on one tank:
  the playthrough must stop and refuel mid-lane, and it must decide to do so at
  `fuel <= jump_fuel`, not `fuel < jump_fuel`, because Stage 8's exact-fuel rule
  refuses a jump whose price exactly equals the tank.
- **Not implemented here, by design, with owners named:** the confirm beep's *volume*
  and the rest of the audio layer (Stage 12 — the spaceport already calls
  `manager.audio.play_confirm()` on successful transactions only, and the tests count
  them through a spy); the victory/game-over treatment of `economy.win_credits` and
  the stranded-fuel rule (Stage 13 — `credits` is read-only and `add_credits()` is the
  only way in, so Stage 13 has one seam to watch); NPC despawn on jump (Stage 10).
- **Gotchas for the next stages.** (1) `PortVisit` is discarded on launch
  (`GameScene._release_finished_port_visit`), so nothing may hold a `Mission` across
  visits — accept by identity, not by remembering. (2) `LandingReport.delivered_anything`
  and `LandingReport.credits_gained` are the counters Stage 13's run-stats screen
  should read; do not re-derive them from `carried_loads`, which is already emptied.
  (3) The spaceport's buttons live in `_accept_buttons`/`_buy_buttons` maps keyed by
  widget — Stage 12's UI beep hook is `_report()`, which is the only place a
  transaction outcome is announced. (4) The spaceport is a full-window repaint: if
  Stage 11's `T` scan or Stage 13's pause draws *under* a modal, it will not be
  visible, and if it draws *over* one, it will be a bug. (5) `can_afford` treats a
  cost of 0 as always affordable — a free service is therefore safe to add, and a
  negative price is a config bug the loader should catch before it gets here.

## Stage 9 review fix — the market belongs to the system entry, not to the landing

Reported in review, and correct: with offers rolled on *landing*, `L` → read the
contracts → `ESC` → `L` re-dealt the whole board for two key presses and no cost.
The port was a free slot machine, and nothing about the play pattern punished
pulling the lever. (The earlier Stage 9 note — "leaving the port discards whatever
was not bought" — described that behaviour as though it were a feature. It was a
loophole with a docstring. Superseded below.)

- **One market board per system *entry*.** `GameScene._enter_system(system)` deals
  the board; it is called on a new game (Alpha) and on every jump
  (`EVENT_ARRIVED`, which already existed and already had a comment inviting Stage
  10's NPC roll to hang off it). `GameScene._open_spaceport()` no longer rolls
  anything — it settles the arrival, raises the modal, and reuses
  `self.port_visit`. `_release_finished_port_visit()` became `_close_port_modal()`:
  it still resets the held-key state (the `KEYUP`-eaten-by-modal bug), but it no
  longer throws the board away. Net effect: launch + re-land shows the same work;
  jump out and back is a new visit and deals a new list.
- **Why per-entry rather than per-run.** A run-scoped `dict[system → board]` would
  also stop the "hop to Charlie and back" grind, but it makes every system's
  market a permanent fixture of the run: revisit a system ten jumps later and the
  jobs you ignored the first time are still sitting there. Per-entry keeps revisits
  meaningful while still making the exploit cost a jump (fuel, time, whatever is
  flying around out there). Explicitly the reviewer's call, recorded here so the
  difference is not "rediscovered" in Stage 14.
- **A derived RNG stream per market, not a shared cursor.**
  `src/model/economy.py::port_rng(run_seed, system, visit_serial)` returns
  `random.Random(f"{run_seed}:{system}:{visit_serial}")`. The market no longer
  draws from `game_state.rng`. Two properties bought at once: the board cannot
  shift because the player burned fuel for ten thousand frames first (a shared
  cursor makes the market a function of play history — and the Stage 7 note about
  not threading one RNG through the whole game applies), and two entries into the
  same system get different boards because their serials differ. `GameScene`'s
  `_market_seed(config)` is `rng.seed` when configured, else a random per-run
  nonce: with a seed, a run's whole sequence of markets is reproducible, which is
  what Stage 14's determinism sweep wants. Streams are now four: graph, gameplay,
  lore, markets.
- **The model needed no change at all, which is the one pleasant part.**
  `begin_port_visit()` is unchanged (a monotonic per-run serial, now bumped per
  entry instead of per landing), and `_accepted_offers` was already a run-scoped set
  that nothing ever clears — so on a cached board, a job that was taken *or already
  delivered* stays greyed out ("Aboard") forever. Without that, this change would
  have introduced a new exploit in place of the old one: same board, same offer
  ids, fare collectable twice. Worth stating out loud because it is now a
  load-bearing invariant rather than a tidy extra: **the accepted-offer set is
  never pruned.** `test_update_takingAJobThenRelaunchingAndLanding_shouldStillShowItAboardNotAvailable`
  and the playthrough's second landing pin it.
- **Side effects, intended:** the board is sized and priced by the hull the player
  had on entry, so "buy the cargo upgrade here, re-land, farm bigger jobs at this
  port" is closed too; a jump arrival spends a market RNG draw even if the player
  never lands (accepted in review, and it is one draw); and `GameScene.port_visit`
  is now non-null for the whole run, so anything reading it must ask *which system*
  rather than *whether a port is open* — the modal state moved to
  `_port_modal_open`. Stage 10, if you want "the system's ships" to follow the same
  rule, the hook is the same line.
- **What the tests now pin (`tests/test_stage9.py`):** the same object identity and
  the same market descriptor after launch + re-land; the accepted job still aboard
  and its button still greyed on the re-opened modal; a *different* market after
  jumping Alpha → Bravo → Alpha, with the per-system entry serials asserted (1, 2,
  3); `port_rng` determinism (same seed/system/entry, different system or entry);
  and a 10,000-frame flight producing a byte-identical Alpha market to a fresh
  scene. `market_descriptor()` exists because asserting on `offer_id` equality
  would prove nothing — the id carries the serial, so two visits never share one.
  `_SpyAudio` grew `play_jump_spinup`/`play_thunderclap`: a scene-level test that
  flies a jump must not trip over the Stage 8 audio calls it never meant to
  exercise.

## Stage 10 — NPCs, factions, and the AI that flies them

- **Six new modules, and what each one is allowed to know.**
  `src/model/physics.py` (pure 2D movement: thrust, drift, turning, the system
  boundary), `src/model/factions.py` (the hostility matrix, the engageability
  filter, the session's `PlayerRelations`), `src/model/weapons.py` (a `Shot`
  record and the rate→cooldown conversion), `src/model/npc_ship.py` (a hull: stats,
  a gun, damage), `src/model/ai.py` (one ship's one frame: face, close, aim,
  trigger), `src/model/encounter.py` (who is in the system, and the fleet's single
  `advance_frame`). The dependency line runs one way —
  `physics ← factions ← weapons ← npc_ship ← ai ← encounter` — and `encounter` is
  the only module `GameScene` talks to. The AI cannot spawn a ship; the spawner
  cannot steer one; neither knows projectiles exist.

- **A fleet belongs to one system visit.** `GameScene._enter_system` now deals
  *both* the market and the traffic, from the same entry serial but different RNG
  namespaces (`port_rng` / `encounter_rng`). Dropping the old `Encounter` there
  **is** the spec's despawn rule: ships do not respawn, do not persist, and a jump
  out and back "does not remember the quantity or types of ships". Landing and
  launching deliberately do **not** re-roll: parking in orbit to make a pirate
  disappear is the same free lunch Stage 9 closed for the job board. During
  hyperspace the fleet is not simulated at all (`_advance_encounter` skips while
  `jumps.is_active`) — those frames are between two systems, and the fleet is
  garbage at the far end anyway. **Stage 11 note: projectiles must be cleared at
  the same boundary.** The ships that fired them stop existing on arrival; a
  missile that outlives its shooter is a ghost.

- **Pirates are hostile to everyone — including other pirates — but they never
  shoot each other.** Two functions, on purpose. `factions_are_hostile` is the
  matrix straight from the spec (Pirate vs everything: hostile; Localhoster ↔
  Bobber: mutually hostile; everything else: not). `factions_can_engage` narrows
  that to "hostile *and* a different faction", and it is what target selection
  uses. Without it a pair of pirates 20px apart would spend the entire encounter
  trading harmless shots with each other while the freighter they can actually
  hurt sails past. Keeping both questions answerable also keeps the matrix honest:
  Stage 12's "who is shooting at me" indicator wants the matrix, not the
  gun-law.

- **The player's grudge is per-session, not per-system.** `PlayerRelations` lives
  on `GameScene` and is handed to every `Encounter`, so a Localhoster you shot in
  Alpha is hostile in Zulu too — the spec says hostility, once earned, is
  permanent, and a per-system relations object would grant amnesia on every jump.
  Nothing in Stage 10 can *cause* a grudge, because nothing can shoot anything
  yet: Stage 11 calls `declare_hostile_to_player(faction)` the moment a projectile
  lands. Pirates are hostile to the player from frame one regardless, which is the
  only reason a pirate ever chases the player before being hit.

- **NPC hulls are the player's *starting* ship × the config multiple.**
  `GameState.starting_stats` is a separate immutable snapshot taken at
  construction, and `roll_npc_stats` works from it. A system that scales with the
  player's *current* hull would quietly rescale the galaxy on every upgrade, so
  "buy Engine Mk.IV" would make the next pirate bigger than the last one. The gun
  (`weapon_fire_rate`, `weapon_range`) is copied verbatim from the starting ship
  because the spec says so ("firing rate and projectile range equal to the
  player's starting stats"). Handling — turn rate, acceleration, top speed,
  `length`, `width` — is not named by the spec and follows the same anchor: it is
  what makes "other ships are roughly the same size as the player's ship" a
  consequence rather than a coincidence, and it is what lets the Stage 3 physics
  gate ("60 frames of thrust from rest reaches exactly top speed") be asserted
  about an NPC as well as the player.

- **NPC fuel is not modelled at all.** "Unlimited fuel" is the *absence* of a
  field, not a field set to a big number: an `NpcShip.fuel` would be state that
  can drift out of sync with the rule it claims to express, and "cannot initiate
  jumps" would need a guard nobody can reach. The test asserts the absence of
  `fuel`, `fuel_capacity`, and any `*_jump` method on both `NpcShip` and
  `NpcStats`, which is the only way it stays absent.

- **Physics moved into its own module so the player and the AI cannot disagree.**
  `GameState` had already grown `facing_vector`, `_apply_thrust`,
  `_integrate_position` and `_clamp_to_system`; those are now thin delegations to
  `src/model/physics.py`, and the NPC hull uses the same functions. Two rules that
  must not have two answers: what "top speed" means, and where the system boundary
  is (`clamp_to_square` zeroes the velocity component that pointed through the
  wall, so an NPC pressed against the edge cannot slingshot).

- **The engagement band, and why the AI must start braking before it gets there.**
  `AiTuning.band_for(weapon_range)` = `engage_range_fraction` × the ship's own gun
  range. Not the range itself: a ship parked exactly on the range circle is one
  float wobble away from deciding its gun is out of range, and the fraction is the
  knob that sets how tightly the fleet crowds in. `choose_motion` is three lines
  (chase / brake / coast) whose middle case is the whole design: at the fixed
  timestep a ship at `v` needs `v²/2a` pixels to stop, so the retrograde burn
  starts that far *outside* the band and the ship arrives standing still.
  This was not a refinement, it was a bug fix. The first implementation burned
  toward the target until it was inside the band, then stopped *thrusting* — and
  inertia carried it straight through the player, out the other side, and back
  again: measured distances of 0px to 1000px, oscillating forever, which on screen
  is a swarm of flies around the player's cockpit. Two things had to change:
  1. **`apply_thrust` cannot be used to brake.** It ignores thrust entirely once a
     ship sits at its speed cap — correct for the player ("the throttle is already
     hard down") — which made a retrograde burn at top speed a *no-op*, so a ship
     chasing at 5px/frame could never slow down at all.
  2. **Braking is its own instruction, not a burn vector.** `physics.brake`
     reduces speed by at most the speed that is left. A plain thrust step larger
     than the remaining speed flips the velocity through zero and the ship
     oscillates around a standstill forever (measured: still drifting at
     0.07px/frame after four seconds of "holding position"). `ShipOrder` therefore
     carries `burn` *and* `brake`, and a brake and a burn are mutually exclusive.

- **"No hostiles: hold position" is an engine burn, not an idle.** There is no
  drag in this universe, so a ship with drift holds position by decelerating:
  4.47px/frame of drift costs its own braking distance (v²/2a = 50px) and then
  exactly zero. A ship that merely stopped thrusting would have crossed the system
  (1,073px in four seconds) while the AI believed it was holding station.

- **Every ship picks its target from the frame's opening snapshot.**
  `Encounter.advance_frame` plans for the whole fleet, then applies the plans.
  Interleaving decide/move would make a ship's target depend on whether its
  neighbour happened to be earlier in the list — spawn-order-dependent behaviour,
  which is the class of bug that survives every test containing exactly one ship.
  The test for this is worth stealing: the Bobber starts facing 45°, exactly
  halfway between two candidates, so a single 3° turn step reveals which one it
  was looking at when the frame opened (42° = the one it chose, 48° = the one a
  decide-after-moving implementation would have picked).

- **The spawn-chance ramp spans the systems *in play*, and the first denominator
  was wrong.** `spawn_chance_for_system` interpolates from
  `spawn_chance_near` at the first system after Alpha to `spawn_chance_far` at the
  last system in the roster, index-wise: `(index - 1) / (last_index - 1)`. The
  first version divided by `last_index`, which looked plausible and meant Zulu drew
  0.676 on a config that said 0.7 — the configured maximum was stranded one system
  past the end of the roster, unreachable forever. `map.system_count` shrinking
  moves the top of the ramp, which is what a Stage 14 sweep would poke. Edge case,
  documented in the code: with only Alpha and one other system there is nothing to
  ramp across, so that system gets the *near* chance; and Alpha's 0% is
  unconditional — no config value can make the starting system dangerous.

- **One coin flip per fleet; spawn positions are rejection-sampled for player
  clearance.** The spec says "a random number of between 1 and 4 ships", not "each
  ship appears with probability p", so `spawn_chance_for_system` is rolled once and
  `ships_min..ships_max` is drawn on success. Positions are re-rolled (up to
  `_SPAWN_REJECTION_LIMIT = 24` attempts) until they clear
  `npc.min_distance_from_player` from the player, then accepted as-is: the spec
  says only "random positions", and the clearance exists so an arrival is not
  instantly inside someone's guns before the player can see the minimap. The
  bounded budget is what stops an impossible clearance (or a tiny system) from
  looping. Because "impossible" is a data error rather than a play condition, the
  loader cross-checks `npc.min_distance_from_player <= tactical.system_pixel_size`
  and refuses to start.

- **Config validation is delegated to the object the spawner actually runs on —
  and that sentence hid a bug.** `config._NpcConfig` has no range checks of its
  own; its `model_validator` builds a `SpawnRules` and lets *it* complain, so the
  loader and the model cannot drift. It did not work: `SpawnRules` is a frozen
  dataclass whose checks lived in `check()`, which `from_config` called and the
  validator did not — so nine parametrised "impossible npc config is fatal at
  startup" tests reported `DID NOT RAISE`. Fixed by moving the call into
  `__post_init__`: an invalid `SpawnRules` object can now not exist at all, from
  the loader, from a test, or from a future save-file reader. Recorded because
  "validation delegated to the model" is only a good idea if the model actually
  validates on construction.

- **What each difficulty actually changes.** easy 5%→45% chance, 1–3 ships, 3.0×
  hull, 6° jitter, band 0.65; medium 10%→70%, 1–4, 4.0×, 4°, 0.75; hard
  25%→95%, 1–4, 5.0×, 2°, 0.9. Because an NPC's gun *is* the player's starting
  gun, NPC damage-per-second is `stat_multiple` × the player's own starting DPS in
  every difficulty — so the curve comes from how often traffic appears, how many
  ships, how tough the hull is, and how tightly and accurately they crowd in, not
  from their rate of fire. `engage_range_fraction` also has a constraint the
  loader deliberately does not enforce: the band must fit inside the system. The
  first tuning used 0.85 everywhere, which on easy is 1275px around the player in
  a system whose half-width is 1100 — every ship in every encounter would park
  against the system boundary rather than hold its band. Nothing crashes, which is
  exactly why it is pinned by a test
  (`testshippedConfigs_engagementBandsShouldFitInsideTheirOwnSystems`) instead of
  by a startup check that would refuse a playable configuration. The related
  visibility question is left open deliberately: the game view is 683x768, so a
  medium-band ship parked 900px out is drawn nowhere at all — the player sees the
  fleet on the minimap only. Shrinking the band would fix the sightline and undo
  the gun range, so the real answer belongs to Stage 11 (off-screen contact
  indicators, or projectiles that visibly come from outside the view). Flagged in
  the README and here so Stage 11 does not "discover" it mid-combat.

- **Faction colour is model data; the HUD no longer owns a private red.**
  `factions.py` carries `FACTION_COLORS`, used by the tactical hulls, the minimap
  markers, and (Stage 11) the projectiles, so a faction cannot be one colour in the
  view and another on the map. `HudView.enemies` (a list of `(x, y)` tuples with a
  hard-coded hostile red) became `HudView.contacts` (anything exposing `.position`
  and `.faction`) — one list published once per frame from `GameScene.draw()` to
  both renderers. `tests/test_stage6.py` was updated to match; the Stage 6
  minimap tests still assert positions, now against a colour that comes from the
  model.

- **Three silhouettes, drawn procedurally, and painted under the player.** Arrow
  (Localhoster), flying saucer with a dome (Bobber), forward-swept pronged raider
  (Pirate) — polygon/ellipse code, no image assets, sized from the player's
  *starting* `length`/`width` and cached once per faction per view (rotating a
  cached surface at 60Hz is cheap; redrawing polygons per ship per frame is not).
  Drawn *before* the player's hull because ships pass through each other in this
  model, so the only question a pixel collision raises is who wins it, and it must
  be the ship the player is steering. The blit is clipped to the game-view rect: a
  hull half off the left edge would otherwise be painted across the HUD column,
  since `blit` is not region-clipped by itself. Contacts are hidden during the
  white-out for the same reason the player is — during hyperspace nobody is in
  this universe — and culled when off-screen, because a 2000px system in a 683px
  view is mostly empty on any given frame.

- **`Shot` is the Stage 11 seam, and there is exactly one cooldown clock.** The AI
  decides *whether the trigger is held*; `NpcShip._release_shot` decides whether
  the gun can honour that this frame, because the cooldown is the gun's state. Two
  owners of the fire rate means two clocks and a ship that shoots at double its
  configured rate. A `Shot` carries faction, owner, origin, aim direction, the
  shooter's velocity (so a projectile inherits the ship's motion, as the spec's
  "projectiles retain the ship's velocity" wants), weapon power and weapon range —
  everything Stage 11 needs to make a projectile without asking the AI anything.
  `GameScene.pending_shots` is replaced every frame and emptied during hyperspace;
  it is deliberately not consumed by Stage 10.

- **One gotcha for whoever writes the next scene-level test.** The input layer is
  edge-triggered and `KEYUP` discards a rising edge that has not been drained yet,
  so `press(J)` + `release(J)` inside one frame is not a tap, it is *nothing*.
  Worse, a `KEYDOWN` that is never released leaves the key held, so a second press
  in the same scene is not a rising edge and a two-hop jump test fails looking like
  the jump controller is broken. `tests/test_stage10.py::jump()` does it in the
  order reality forces: press → `update()` (drains the edge) → release → run to
  arrival, and raises if the scene never got there.

- **A picture of the whole stage.** `scripts/capture_npc_fleet.py` (same shape as
  the Stage 8/9 capture scripts) hand-places one ship per faction, runs the
  encounter, and emits `stage10_npc_fleet.png`: empty Alpha, a rolled fleet that
  is real but off-screen (minimap dots only), a pirate entering the view at the
  left edge, the fleet settled exactly on its band, the three silhouettes up
  close, and hyperspace with nobody in it. It narrows `weapon_range` to 400 so the
  engagement fits in the view — see the visibility note above. Hand-placed rather
  than rolled on purpose: if the fleet were rolled, every future change to the
  spawn rules would change the pictures, which is the opposite of a visual diff.

## Stage 11 — Combat and the `T` scan

- **Two new model modules, and the one thing each owns.** `src/model/combat.py`
  is the fight: `CombatRules` (the validated `combat` config section), `Projectile`
  (one round in flight, in world coordinates), `Combatant` (a body a round may
  hit), `Impact` (what happened when one met the other), `Bounty`,
  `bounty_for_kill`, the swept hit test, and `Gunfight` (the round list and the
  per-frame resolution). `src/model/scan.py` is `ShipScanner`, the sticky lock
  behind `T`. Neither imports pygame; neither knows the scene exists. `Gunfight`
  is fed its targets every frame rather than holding references to them, because
  the fleet's lifetime is not its business: a `Gunfight` that owned ship objects
  would keep a wreck alive out of spite, and a scene that forgets to update the
  list gets a stale battlefield instead of a type error.

- **The player is a combatant, never a faction.** `factions.py` grows
  `FACTION_PLAYER` plus `COMBATANTS`, `require_combatant`, `combatant_color` and
  `is_npc_faction`, and `FACTIONS`/the hostility matrix stay exactly as Stage 10
  defined them. The distinction is load-bearing: the matrix answers "does this
  faction shoot that faction", and the player's relations are a separate mutable
  thing (`PlayerRelations`). Letting `"player"` into the matrix would let code ask
  a question the table cannot answer and get `False` — silence where the answer
  should be an error. `Shot.faction` therefore *may* hold `FACTION_PLAYER` (the
  field name is kept from Stage 10 rather than adding a second "who fired" field:
  two provenance fields, one of which is always empty, is how the wrong one gets
  read).

- **`combat.projectile_radius` → `combat.projectile_diameter`, in the same change
  as the code that reads it.** The spec fixes a round at "3px diameter" and pygame
  draws circles by radius. The key now names the value's meaning, and the
  conversion (`diameter // 2`, floored at 1 so a round is never a single invisible
  pixel) happens in exactly one place: `CombatRules.projectile_radius`. All three
  shipped configs were renamed in the same edit, and the old key is fatal at
  startup (`extra = "forbid"`), pinned by
  `testloadConfig_withTheRetiredProjectileRadiusKey_shouldFailAsAnUnknownKey` — a
  half-renamed
  config that silently keeps the old key is the boring way for the shipped
  difficulties to stop matching each other. No other keys were added: the `combat`
  section already existed, so the fixtures needed no new defaults.

- **One fire-rate clock, and the cycle length handed in at the trigger.** Stage 10
  kept a cooldown inside `NpcShip`; Stage 11 gives the player a gun, so
  `weapons.WeaponClock` is now the single implementation and both hulls use it. It
  counts *frames* and takes the cycle length as an argument to `pull()`, rather
  than storing a fire rate. Writing the upgrade test is what exposed the mistake:
  a clock that memorises `weapon_fire_rate` at construction keeps the boot-time
  rate for the whole run, so a bought upgrade changes the shot's power and range
  but not its rate — the same staleness the `Shot` already avoids by carrying live
  stats. `GameState.gun_cooldown_frames` reads the live stat block, and
  `NpcShip.weapon_ready` now reports `False` for an infinite cycle so readiness and
  firing cannot disagree. A disabled gun also gets no free first shot: a clock born
  ready with a zero fire rate fires exactly once, which is a bug that only appears
  in a config somebody edited by hand.

- **`apply_damage_order` lives in `stats.py`, and does not clamp.** Shield-first
  is one rule with two callers (an NPC hull and the player's hull); two
  implementations is how a game ends up where the player and the NPCs are playing
  different games. It returns `(shields, armor)` and refuses to floor armour at 0:
  overkill is information the caller may want (a destruction banner, a later
  "how badly did I win that fight" readout), and a helper that quietly discards
  the excess is a helper the caller cannot trust with arithmetic.

- **Hit detection is swept, and that is not an optimisation.** A round on the
  shipped medium tuning moves 13px/frame from a hull whose hitbox is 20px in
  radius; a fast ship (or a fast round) steps clean over a target between two
  frames, so a point-in-circle test reports a miss the player can *watch* happen.
  `segment_entry_parameter` solves the segment/circle intersection and returns the
  earliest `t` in [0,1]; `Gunfight` picks the *smallest* `t` among the bodies it
  may hit, so when one sweep crosses two hulls the one entered first takes the hit
  regardless of the order the target list was built in — the same spawn-order
  class of bug Stage 10 pinned for the AI's target choice. Consequences that are
  now pinned by tests: a round damages at most one hull (no perforating a
  formation); a round that expires and lands on the same frame counts as a hit
  (resolving the hit first is what makes `weapon_range` the honest number rather
  than one pixel short of it); the `Impact.position` is the entry point, which is
  where the sparks go. Documented edge case: a round *born inside* a hull (hulls
  overlap; there is no hull-on-hull collision in this game) has entry `t = 0` and
  hits at the muzzle point — "you were inside me, therefore my gun does nothing"
  is the worse of the two rules.

- **`_advance_gunfight` moves the old rounds before launching the new ones.** The
  frames already in flight are resolved against the bodies standing where the frame
  *opened* (the same snapshot discipline the fleet's AI uses), and this frame's
  shots are launched afterwards. Otherwise a ship sitting inside another ship's
  hitbox scores a point-blank hit on the frame its round was born, and a muzzle
  flare is not yet a hit.

- **A hit is a diplomatic incident; a collision is not.** A player round that
  lands on a Localhoster or a Bobber declares hostility for the rest of the game —
  on the *impact*, not on the kill, because a shield that soaked the hit changes
  the galaxy just as much as a hull that did not survive it, and only the *victim's*
  faction takes the grudge. A stray NPC round from a faction at peace with the
  player damages the player and does **not** flip relations: the player did nothing
  to anyone. That asymmetry is why the round's colour matters at all, and it is the
  only cue the player gets — hence projectiles, sparks, hulls and minimap markers
  all take their colour from `combatant_color`. Grudges are recorded *before*
  bounties are computed. They cannot actually interfere (a hit makes the victim
  hostile; the bounty depends on the *payer's* relations, and the payer is the
  victim's enemy), but the order that cannot interfere is the order worth writing
  down.

- **Bounties are keyed to the victim and paid by the victim's enemy.**
  `combat.pirate_bounty` / `bobber_bounty` / `localhoster_bounty` name the hull
  that died, which lets a config price the two war-sides separately without a
  second table; `war_side_of(victim)` decides who thanks the player, and the
  bounty is simply not offered when that payer already hates them ("make enemies of
  both war-sides and neither pays"). A pirate bounty comes from the game and has no
  relations check, because pirates have no rival to send their regards. A zero
  bounty is silent rather than announcing `0K bounty paid!`. `Impact.fired_by_player`
  is identity-based (`shot.owner is game_state`) and settled upstream, so the
  spec's "no reward when another ship's projectile lands the final blow" is a fact
  about who fired rather than a guess from who was nearby.

- **Scan lock is scene state; the HUD is a painter.** `GameScene.scanner` owns the
  lock and `GameScene.draw()` publishes `scanner.displayed` to
  `HudView.nearest_ship`. A HUD that picked "the nearest ship" itself would be a
  second scanner, and the two would disagree the first time a pirate flew past the
  hull the player was watching. Per frame, `refresh()` drops the lock *only* if the
  displayed hull was destroyed — the spec's revert to `No target` is not
  conditioned on another `T` press. `_enter_system` calls `clear()`, which closes
  the Stage 10 note about locks surviving a jump. `scan()` (a `T` press) re-locks on
  the current nearest: the stickiness the spec asks for is about the frames between
  presses, and a `T` that did nothing would leave the player staring at a pirate
  who fled across the system.

- **Deaths are pruned once, in one place.** `Encounter.prune_destroyed()` runs at
  the end of `_resolve_impacts`, before the scan refresh and the bounty check, so
  the fleet, the minimap, the readout and the payout all ask "is that hull still
  flying?" of one answer. `nearest_living_ship` was lifted out of
  `Encounter.nearest_ship_to` and is shared with `ShipScanner`, so "nearest" cannot
  mean "nearest, wrecks included" in one module and the opposite in another.

- **The planet is not a target, at all.** `_battlefield()` returns the player plus
  the fleet and nothing else. A `Combatant` standing in for the planet with an
  `immune` flag would need that flag to be honoured by every future code path; the
  absence of the object is the rule, and
  `testscene_aRoundCrossingThePlanetShouldPassStraightThrough` fires a round
  through the disc to keep it that way. Landing, launch immunity, jumping and
  destruction use a *live* `immune` flag on `Combatant` instead — those are states
  of a body that is present.

- **Dying stops the run, and stops the ship.** The frame armour reaches 0,
  `GameScene._note_player_destruction` locks input, prints `Ship lost with all
  hands!`, and sets `pending_game_over`; a destroyed hull is dropped from the
  battlefield, so a wreck gets no last shot and takes no further impacts. The end
  screen itself is Stage 13's, and the flag is deliberately the only thing this
  stage raises.

- **Off-screen contact indicators were not added — and that was the offer.**
  Stage 10's notes handed Stage 11 a choice for the fact that a medium-band ship
  parks 900px outside a 683px view: draw off-screen contact arrows, or let
  projectiles visibly come in from outside the view. This stage took the second
  option, because the rounds already exist, are faction-coloured, and are already
  world-anchored and drawn through the shipping camera; a new HUD affordance is a
  bigger promise than the spec's Stage 11 asks for. Consequence: in the shipped
  tuning the player can be shot from off-screen with no hull in view, and the only
  warning is the round itself (and the minimap). `scripts/capture_stage11_combat.py`
  narrows `weapon_range` to 420px so the sheet shows a whole fight, which is a
  capture-config trick and not a shipping change. If a later stage wants on-screen
  bearing indicators, the data is already in `Gunfight.projectiles`.

- **Particles are presentation state owned by the view and fed by the scene.**
  `src/effects.py` gained `ParticleBurst` / `_Particle` / `ImpactEffects`, owned by
  `TacticalView` (like the starfield and the warp tunnel: view state, not model
  state) and spawned by `GameScene._resolve_impacts` through
  `show_impact` / `show_destruction`. Sparks are stored in **world** coordinates
  and drawn through `world_to_screen`, so a burst stays where the hit happened;
  `ImpactEffects.draw` obeys the same `ship_visible` rule as the starfield, so
  nothing burns inside a jump, and `notify_system_changed` clears them, because a
  burst drawn in the wrong system is a coordinate bug the player sees as a ghost.
  Bursts are tinted with the *firer's* colour over a fixed hot-spark palette: the
  palette says "explosion", the tint says "who did this", and reusing faction
  colours for the palette would make a pirate's death indistinguishable from a
  pirate's shot. An impact is 12 particles at 2.6px/frame over 22 frames; a
  destruction is 40 at 6.0px/frame over 48 — "larger" is particle count and spread,
  not dot size. One silent tuning call, recorded: `_IMPACT_RADIUS` is 2 rather than
  1, because a radius-1 spark is a 3px smudge against the starfield and a hit that
  cannot be seen cannot warn anybody. Burst parameters are code constants, not
  config keys — the spec fixes the round's 3px diameter and says nothing about the
  size of an explosion, and a knob nothing tunes is a key every config file has to
  carry. If Stage 12's audio or a settings screen ever wants them, they land as
  config keys with the fixtures in the same change, as usual.

- **The readout grew two bars, so its block grew too.** `hud.NEAREST_SHIP_ROWS`
  (`alignment`, `shield`, `armor`) is the single source for the readout's height:
  `NEAREST_RESERVE` is derived from it *including* the inter-row `GAP`, because
  `ship_status_row_rects` spaces rows with gaps and a reserve without them let the
  armour bar bleed 24px into the cargo panel. The bars themselves go through the
  same `status_row_geometry` and `HudView._draw_bar_row` as the player's own Ship
  Status block, which is the only way the spec's "displayed similarly to the bar in
  the player's own Ship Status component" survives either block being edited. There
  is deliberately no third (fuel) bar: an NPC hull has no fuel, and a bar for a
  stat that does not exist is a readout lying. The alignment word is painted in the
  faction's colour — the colour *is* the warning, and it comes from
  `combatant_color`, not from a second HUD palette.

- **Test patterns worth copying.** Hermetic throughout: fabricated configs via
  `base_config()` plus section overrides (never the shipped JSON), the dummy SDL
  drivers from `conftest.py`, and a seeded RNG so `hull()`'s stat rolls and the
  particle jitter are reproducible. Two non-obvious ones: pixel assertions count
  *changed* pixels between two canvases of the same view at the same camera
  (`_changed_pixels`) rather than lit pixels — the starfield, planet, ship and HUD
  are all painted too, so "how many pixels did the effect change" is the only
  question with a trustworthy answer; and the capture script records the scene's
  presentation calls (`show_destruction`, `show_message`) to decide *when* to
  photograph, which is cheating about timing but not about content. The capture
  also raises the player's armour on the **live** stat block rather than in the
  config, because `roll_npc_stats` works from the player's *starting* stats and a
  config boost puts 1000 points of armour on every pirate in the picture (the
  resulting standoff is a funfair, not a fight).

- **What Stage 11 deliberately does not have.** No sound for gunfire, impacts or
  deaths (Stage 12's audio seams exist — `_SpyAudio` in the scene tests is the
  pattern the next stage will use). No "who is shooting at me" indicator, no
  reputation or faction-standing display beyond the readout's alignment word, no
  wrecks or debris fields, no shields-regenerating-over-time, no missile or
  homing weapons, and no end-of-run screen. `BOUNTY_MESSAGE_FRAMES` is currently
  shared by the bounty banner and the "Ship lost with all hands!" banner; that is
  one constant serving two unrelated pieces of copy, and it should be split the
  first time either duration changes.
