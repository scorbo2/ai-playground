# Decisions

What follows is a record of decisions made by the implementing LLM
to handle anything that the spec didn't make explicit.

## Stage 1 — Walking skeleton + tooling

- The three config files use the full key set from the spec sketch, with
  medium values as the base and easy/hard tuned per the dev plan (easy:
  generous economy and better starting ship stats with lighter fuel usage;
  hard: smaller fares, faster fuel burn, pricier upgrades, weaker starting
  ship stats). `win_credits` is the same 1,000,000 in all three files.
- The ambiguous two-element fare lists (`economy.cargo_fare_per_unit`,
  `economy.passenger_fare_each`) are interpreted as the minimum and maximum
  per-unit fare rates; a mission fare = units * rolled rate * far-destination
  multiplier (far-destination bonus applied as a multiplier on the rolled
  fare).
- The schema is enforced with pydantic models (`extra="forbid"` so
  unrecognized keys are fatal, required fields so missing keys are fatal);
  numeric fields accept ints and floats as written in the config.
- The stage-1 main loop is a no-op skeleton: fixed 1/60 step with a bounded
  accumulator (limit 5/60), real dt ignored, window created before the loop
  starts. UI/scene/game logic is added in stages 2 onward.
- ESC quits the stage-1 window (no title screen exists at this stage).
- `resources/title_screen.png` is generated by
  `scripts/generate_title_screen.py` (dark 1024x768 gradient) so the title
  screen background exists at startup.
- The headless test harness runs under `SDL_VIDEODRIVER=dummy` and
  `SDL_AUDIODRIVER=dummy` via the root conftest.py, plus a
  `config_factory` fixture and `pump_events`/`advance` helpers in
  `src/harness.py`.

## Stage 2 — Scene manager + title screen

- **Scene stack design**: a `SceneManager` holds a list-based stack of `Scene` objects.
  Only the top scene receives `handle_event()` and `update()`. All scenes are drawn
  bottom-to-top so modal overlays (e.g. the difficulty dialog) appear correctly layered
  over the scenes beneath them.
- **Difficulty dialog**: implemented as a `DifficultyDialog` scene pushed on top of the
  `TitleScene`. It draws a semi-transparent overlay so the title is visible behind it.
  Selecting a difficulty pops the dialog, then replaces the `TitleScene` with a
  `PlaceholderScene`, leaving a single-entry stack.
- **PlaceholderScene**: a temporary stub scene used as the Stage 2 gate target. It will
  be replaced by the full tactical display in Stage 4. ESC returns to the title screen.
- **Audio**: `AudioSystem` is a fail-soft singleton constructed in `main()` and stored on
  the `SceneManager`. Scenes access it via `self._manager.audio`. The confirmation beep is
  generated with `stdlib.array` + `pygame.mixer.Sound(buffer=...)` as required by the spec.
- **`FixedTimestepLoop` refactored**: the loop now accepts an optional `scene_manager` and
  `screen` parameter; `on_step` is kept for stage-1 backward compatibility. When a
  `SceneManager` is supplied, events are routed to it and it drives update + draw each frame.
- **Window caption** ("The velocity of escape") is set in `main()` via
  `pygame.display.set_caption()` once the display surface is created.


## Stage 3 — Pure model core (no pygame)

- **`GameState` takes a flat merged config dict**, not the loader's filename-keyed dict. `load_config()` returns `{filename: values}`; gameplay needs one difficulty's flat values, so tests extract `loaded["config_easy.json"]`.
- **Reverse-course frame count is derived from `turn_rate_deg_per_sec`** (default 180°/s → 3°/frame at fixed 60FPS → exactly 60 frames for a 180° flip). This keeps the behaviour config-driven rather than hard-coded.
- **Thrust caps velocity magnitude by rescaling**, not naive clamping: when the acceleration step would push speed over `top_speed`, the velocity vector is scaled down to land *exactly* on `top_speed`. Naive accumulation left it at `4.9999…`; rescaling yields exactly `5.0`.
- **Fuel burn** comes from `tactical.fuel_burn_per_frame` and is consumed once per thrusting frame. Reverse-course flips and inertial drift consume no fuel. Fuel is clamped to zero and has a clamping setter so it can be set/patched in tests.
- **Reverse-course is a pure rotation**: no thrust, no fuel, no velocity or position change. While flipping, left/right arrow rotation is ignored (the auto-flip takes priority).
- **Reverse-course restart semantics**: pressing Down while idle begins a flip from the current heading; pressing it again mid-flip resets the flip origin to the current heading and continues toward a fresh +180° target (so completion takes another full 60 frames, ending at `start + 210°` in the test).
- **Coordinate convention**: world coordinates are planet-centred — the planet sits at `(0, 0)` and the system boundary spans `[-system_pixel_size/2, +system_pixel_size/2]` on each axis. Positions/velocities are offsets from the planet. This is the convention `world_to_screen` in Stage 4 will map to screen space.
- **Heading** is stored as a raw degree value and normalised to `[0, 360)` via `heading_degrees`. Completion checks use a small epsilon (`1e-9`) so float drift doesn't cause a flip/thrust to stop one frame short.

## Stage 5 — Input layer

- **`src/input.py` owns the raw-key → control/action translation.** The `InputLayer` consumes pygame `KEYDOWN`/`KEYUP` events via `feed_event()` and, once per real frame, exposes a `ControlFrame(thrust, left, right, reverse_edge)` plus a list of discrete `Action` objects. This cleanly separates key handling from simulation: the tactical scene feeds raw events into the layer, then asks the layer to drain a frame.
- **Binding table (edge-triggered actions):** `space` → `fire`, `m` → `open_map`, `j` → `jump`, `l` → `land`, `t` → `scan`, `escape` → `exit_game`. Left/right/up are *level* control signals; down is an *edge* signal (rising edge only, so holding does not re-trigger).
- **`fire` is level-hold**: pressing and holding space emits one `fire` action per drained frame while held, supporting a configurable rate-of-fire later. The other five bindings are strictly edge-triggered (emit once per physical press).
- **Input-lock flag:** when set (a jump is in progress), `drain_frame()` returns `None` for the control frame and an empty action list — every control and binding is suppressed for that frame, and any queued actions are discarded so they cannot leak to the next frame.
- **`ControlFrame` vs `GameState.InputFrame` duplication:** these are two small 4-boolean dataclasses living in different layers. I deliberately did *not* have the pure model import `input.py` (which imports pygame), because Stage 3's gate requires the model core to stay free of pygame. The tactical scene maps `ControlFrame` → `feed_input(**kwargs)`. Documented here to avoid "silent" duplication.
- **TacticalView wiring:** `handle_event()` now delegates to `self.input.feed_event(event)`; `update()` drains the frame, feeds controls into `game_state`, and dispatches actions through `on_action()`. Actions that belong to later stages are accepted but currently routed to a no-op (with an optional confirm beep) so nothing half-built is wired up.

## Stage 4 — Tactical view, camera, starfield

- **`TacticalView.__init__(self, manager)`** takes the manager at construction (unlike the title/difficulty scenes, which set up state in `on_enter`). The tactical view needs its config/game state/ship sprite immediately, and the stage-4 tests construct it directly. `on_enter` is now a no-op passthrough so there is no double setup when the scene manager pushes/replaces it.
- **Flat config access**: `TacticalView` reads the flat merged config via `manager.configs["config_easy.json"]`, matching how `main.py` wires the loader's filename-keyed dict to gameplay. `GameState` still receives that flat dict (per the Stage 3 decision). *(**superseded** — see "Stage 6 review fixes" item 8: hard-coding the easy file made every difficulty play the easy game.)*
- **View geometry is hard-coded in code** (`VIEW_WIDTH = 683`, centre at `(341.5, 384)`), because window size/dimensions are chicken-and-egg exceptions per the spec and must not depend on the config being loaded first.
- **Starfield recycling**: a star is recycled only when it goes *strictly outside* the visible `[-half_extent, +half_extent]` box; respawn places it inside an inset box of `[-(half_extent - spawn_margin), +(half_extent - spawn_margin)]`. With `spawn_margin` equal to a controlled movement distance, no star ever leaves during that movement, so the "shift left by exactly delta" invariant holds deterministically without recycling interference. Default `spawn_margin = 0` keeps the full view populated in gameplay.
- **Planet colour** is chosen deterministically from `planet_diameter % len(_PLANET_COLORS)` (dicts are unhashable, so no `hash()` on config).
- **Ship sprite**: a cached, procedurally drawn blocky cargo shuttle sized to `player_ship.length` × `player_ship.width`; each frame a rotated copy is blitted centred on the ship's world position mapped through `world_to_screen`.

## Stage 6 — HUD + minimap + landing prompt

> **Historical record.** The first Stage 6 revision contained real defects that the
> stage gate did not catch. Where a bullet below contradicts the
> "Stage 6 review fixes" section at the end of this file, **the review-fixes section
> wins**; superseded bullets are tagged inline rather than deleted so the reasoning
> that produced them stays visible.

- **HUD is the right third of the window** (341 px wide = `1024 - 683`), implemented as a separate `HudView` scene pushed *after* `TacticalView` in the stack, so it draws on top and owns only the region `x >= VIEW_WIDTH`. This keeps the game view and HUD cleanly separated; each scene clears only its own region. *(**superseded — this froze the game**: only the top scene receives `handle_event()`/`update()`, so a passive HUD on top of the stack swallowed every keystroke. The HUD is now a component of `GameScene`; see review fix 1.)*
- **`TacticalView.draw()` now fills only the left game-view rectangle** (`[0, VIEW_WIDTH]`) instead of the whole surface. Previously it wiped the entire screen black each frame, which would clobber the HUD drawn by `HudView`. Overlays added later (e.g. jump feedback) are confined to the game-view rect for the same reason.
- **HUD palette and border styling live in code**, not config — even though the Stage 6 prose says "palette from config". The overarching spec rule explicitly lists "colors-as-defaults" as something that should live in code, so I kept a small `_HudPalette` (dark background, light-green text/bars, gray 2px borders) in `hud.py` and did *not* add a `hud` section to the config schema. Adding config keys would have required touching the pydantic model + all three shipped configs + `base_config()`, for styling that is better owned by presentation code. Recorded here so this "palette from config" wording isn't silently dropped.
- **Pure functions are the testable core.** `bar_width()`, `navigation_status_text()`, `navigation_is_bold()`, `planet_arrow_direction()` (unit vector ship→planet), `arrow_quadrant()` (all four quadrants), and `minimap_scale()`/`is_planet_off_map()` live in `hud.py` with no pygame dependency, so the gate's bar-width/status-string/arrow-direction/layout tests run headless. *(**partly superseded** — `arrow_quadrant()` was deleted: it returned a quadrant label instead of a vector, was never called by the renderer, and its tests only asserted the helper against itself. `planet_minimap_marker()` + `planet_arrow_points()` are the live path now.)*
- **Minimap scale** fits the *whole system* into the minimap's half-width: `scale = minimap_half / (system_pixel_size / 2)`. The ship sits at its world position and the planet anchors the map centre. If an entity's scaled position falls outside the minimap half-extent in either axis, it is "off-map" (`is_planet_off_map`) and gets a coloured marker (`PYRITE` for the planet, `STAR` for stars) at its scaled slot rather than a single direction arrow. *(**superseded** — the map is player-centred and off-map planets become a large arrow; see review fix 4.)*
- **Enemies, cargo, credits, and nav-selection are read from `HudView` attributes with empty/zero defaults** (e.g. `self.enemies`, `self.nav_selected_name`). They don't exist in `GameState` yet (Stages 7/9/10/11), so later stages populate these attributes rather than reaching into unrelated modules. Stage 6 only wires the ship-status bars, which *do* exist (`fuel`, `stats.shields`, `stats.armor`).
- **`GameState.off_map_positions`** is a new public dict (default `{}`) holding world-coordinate positions of entities pushed past the map edge, keyed by type. It is read read-only by the HUD minimap; later stages populate it instead of reaching into presentation code. *(**removed** — no stage ever wrote to it, and "the HUD asks the model for positions the HUD itself computes" is backwards coupling; see review fix 4.)*
- **Landing prompt** ("Press L to land here") is a pure helper `landing_prompt_text(game_state, planet_pos)` returning the message when within `landing_range`, drawn over the game-view rect by `TacticalView`. *(**superseded — it was never drawn**: the helper had callers only in tests. The live path is `TacticalView._update_landing_prompt()` → `MessageOverlay`; see review fix 5.)*
- **Ship status bars are horizontal and number-free.** Each row lays out a label then its bar side by side (spec: "labels on one row each, with a simple bar display next to each (no numbers)"). All three rows share the same left edge so every bar starts after the widest label ("shield"/"armor", 5 chars) and they all align. Rows are `LINE_HEIGHT` tall — not the old `BAR_HEIGHT` — so the ~18px label fits inside its own border box instead of overflowing it. Bars fill proportionally to `current / capacity`, using the new `max_shields`/`max_armor` capacities on `ShipStats`.
- **Navigation status got a taller box.** Its cached rect height was raised from `BAR_HEIGHT` (8px) to `LINE_HEIGHT` so the 2px border can actually enclose the "No destination" text, and the glyph is centered vertically inside. Same fix applies conceptually to the nearest-ship readout.
- **HUD text must render opaque.** ~~`SysFont(...).render()` returns an `SRCALPHA` surface whose glyphs carry low coverage alpha (~20/255); blitting that onto the game's non-alpha display surface alpha-blends it toward black, washing out every HUD glyph. All font renders now call `.convert()` (strips the alpha channel → opaque), and this was caught by a pixel-exact smoke test rather than remaining a visual surprise.~~ *(**wrong, and the cause of an ugly bug**: `.convert()` deletes the coverage, so every string blitted as a solid filled rectangle of its own colour. See "Manual-testing visual fixes" below.)*

## Stage 6 review fixes (post-review, before Stage 7)

A review of Stages 1-6 against `localhost-challenge-tweaked.md` found nine
"do-not-skip" defects in Stage 6. All nine are fixed here; the suite went from 95
to 143 tests. Each entry records *why*, because most of these were invisible to
the existing per-stage tests.

1. **The HUD is a component of `GameScene`, never a scene-stack entry.**
   `SceneManager` deliberately routes `handle_event()`/`update()` to the top scene
   only (Stage 2 decision), so pushing the input-free `HudView` above
   `TacticalView` starved the simulation: 60 frames of held Up+Left left the ship
   at `(0, 0)` with 1000 fuel and an empty input layer, while the suite stayed
   green. New `src/scenes/game_scene.py` composes `TacticalView` + `HudView`; the
   difficulty dialog now `replace()`s the title with `GameScene`, leaving exactly
   one scene on the stack. *Rejected alternative:* make `SceneManager` update every
   scene on the stack — that breaks the modal semantics the map/spaceport/game-over
   stages depend on (a modal must block gameplay input), and the stack order already
   expresses it.
2. **`main_loop` stopped knowing scene classes.** It had grown a
   `manager._stack[-1]` poke and an auto-push of `HudView`; a loop that imports
   scene types silently re-couples the layers. In its place:
   `FixedTimestepLoop.step_once(events=None, dt=FIXED_DT) -> bool` plus a thin
   `run()` that only owns the 60FPS clock. `step_once` is the seam the integration
   tests drive, so the wiring it exercises is the wiring that ships.
3. **One `GameState` per play session.** `GameScene` creates it from the selected
   config and hands the *same object* to the tactical view and the HUD;
   `HudView.__init__(manager, game_state)` raises on `None`. The HUD used to build
   its own `GameState`, so bars/minimap reported a phantom ship that never changed
   while the real one flew off.
4. **The HUD column is cleared, and so is every panel interior.** `HudView.draw()`
   fills `x >= VIEW_WIDTH` with the HUD background before drawing anything, and
   `_panel()` fills a component's box before stroking its 2px border, so the
   difficulty dialog's translucent panel can no longer bleed through permanently
   (observed: pixel `(690, 500)` read `(30, 30, 50)` forever; now `(0, 0, 0)`).
   Clearing the row boxes is also what makes a *shrinking* bar visible: without it,
   the previous (longer) fill survives the redraw and fuel/shield/armor read as
   permanently full. While in there: the border stroke used `rect.right`/`rect.bottom`
   instead of `right - 1`/`bottom - 1`, leaving the bottom and right edges unstroked.
5. **Minimap is player-centred, per spec.** White 2x2 ship fixed at the map centre,
   green 4x4 planet offset by `(planet - ship) * scale`, red 2x2 contacts, and a
   *large arrow* when the planet is off-map (`planet_minimap_marker()` chooses
   marker-vs-arrow, `planet_arrow_points()` builds the triangle). The previous
   planet-centred map drew the ship 3x3 near the centre, never showed the planet,
   and blitted "off-map" markers at their unscaled coordinates (one landed at
   x = 1405, i.e. off-screen). Off-map contacts are now culled. `arrow_quadrant()`
   and `GameState.off_map_positions` were deleted rather than kept as test-only
   helpers: a pure helper that the production path never calls is a second,
   unenforced implementation of the truth.
6. **The landing prompt actually appears.** `landing_prompt_text()` had test callers
   and no production caller. `TacticalView._update_landing_prompt()` now feeds it to
   a new `src/overlays.py::MessageOverlay` (sticky text + transient banners,
   de-duplicating, frame-budgeted, confined to the game-view rect). Stages 8/11 get
   the banner seam ("System boundary reached", payouts, etc.) instead of each
   inventing their own text drawing.
7. **Sprite rotation: degrees, and the right sign.** `pygame.transform.rotate` takes
   *degrees, counter-clockwise*; the code passed `math.radians(heading)`, so the
   sprite barely moved (`rotate(radians(90))` left the nose pointing east: nose
   centroid offset `(+14.5, -1.0)`). It is now `rotate(-heading)`, negated because
   the model's heading is clockwise-positive in a y-down screen space
   (`heading 0` = east, `heading 90` = south). Verified nose centroid offsets:
   0° `(+14.5, -0.5)`, 90° `(-0.5, +14.5)`, 180° `(-15.5, -0.5)`, 270° `(-0.5, -15.5)`.
   Related: held Left/Right were signed the wrong way (Left *increased* heading, i.e.
   turned clockwise). Left now decreases heading; the reverse-course flip still
   rotates in its original direction, so Stage 3's timing tests are unchanged.
8. **Starfield scrolls, camera follows the ship.** `TacticalView.update()` calls
   `starfield.update(vx, vy)` (it was never called, so the starfield was a static
   wallpaper), and `world_to_screen(world_x, world_y, ship_position, view_center)`
   pins the *ship* to the view centre, sliding the planet past it (spec: "the
   player's ship is always centered and zoom is fixed"; the planet must be
   something the player flies *to*). Stars stay in view space rather than being
   world-anchored: `Starfield`'s tested "shift by exactly delta" invariants are
   frame-relative, and world-anchoring them under a ship-locked camera would double
   the scroll. Star box half-extent is `max(VIEW_WIDTH, 768) / 2` so the taller axis
   is not star-free.
9. **The selected difficulty is honoured.** `SceneManager.game_config()` returns the
   flat dict for `selected_difficulty`, falling back to
   `DEFAULT_DIFFICULTY_CONFIG = "config_medium.json"` if a game somehow starts with no
   selection. Both the tactical view and `GameScene` use it; the previous literal
   `configs["config_easy.json"]` lookups made easy/medium/hard byte-identical in play.
10. **Integration tests exist.** `tests/test_game_flow.py` drives the real
    `FixedTimestepLoop.step_once()` with real posted pygame events: title →
    difficulty click → `GameScene` on a one-entry stack, hard-config values actually
    reaching the ship, thrust moving the ship and burning fuel, rotation/reverse
    through the whole pipeline, HUD column free of dialog residue, QUIT stopping the
    loop. Every other stage test calls `scene.update()`/`draw()` directly, which is
    exactly the hole the frozen-game regression fell through.

Small things fixed because leaving them would have re-broken the above:

- **`src/fonts.py`** caches `SysFont` (`game_font(size, bold)`) and centralises the
  `.convert()` requirement; `hud.py` was constructing a fresh `SysFont` on every
  render call (several per component per frame).
- **Ship sprite nose**: the rear wings were drawn at `3 * length / 4`, which is where
  the nose block begins, so the wings painted the nose out and every heading looked
  identical. Wings moved aft, nose drawn last (200 nose pixels now survive at every
  heading).
- Dead imports/pruned helpers in `main.py`, `hud.py`, `tactical_view.py`,
  `starfield.py`, and the stage tests.

Deliberately **not** fixed in this pass (each is a later stage's job or an open
design question, recorded so it does not get lost):

- **`GameState.boundary_reached_this_frame()` always returns `False`.**
  `_boundary_reached_this_frame` is initialised and never written. `on_boundary()`
  does work, and the spec wants no wall — it wants a message at most once every five
  seconds, which is Stage 8; whoever implements it must either drive that flag or
  delete the accessor rather than leave a stub that silently lies.
- **`rng.seed` from config is never applied.** Nothing calls `random.seed()`; and
  since the starfield now draws numbers from `GameState.rng` (one RNG per session, on
  purpose, for reproducibility), any future seeding must happen *before* the tactical
  view is constructed, or be re-applied per system in Stage 7 — seeding later changes
  the star layout too.
- **`stats.max_shields` / `max_armor` are captured from the config at construction.**
  The HUD reads capacity live, so Stage 12 upgrades must update the `max_*` fields or
  the bars will misreport; nothing enforces that coupling yet.
- **`economy.missions_min/max` in the shipped configs fall outside the spec's example
  range** (easy 6-10, hard 3-5 vs the spec sketch's 4-8). Plausible as a difficulty
  knob, but the pydantic schema has no numeric bounds at all, so no config range
  violation is currently detectable.
- **The accumulator drains at most one step per frame** (`if
  self._accumulator >= FIXED_DT: self._accumulator -= FIXED_DT`), so a frame slower
  than 1/60 s silently loses simulation time. The bounded accumulator is
  spec-mandated; the "never more than one step" part is an implementation choice that
  Stage 9+ (combat timing) may care about.
- README/docs pass and the remaining review backlog (fuel-sufficiency landing rule,
  system-boundary messaging) are untouched on purpose: one stage at a time.

## Manual-testing visual fixes (two glitches found by eye, not by the suite)

Both of these survived 152 green tests because the suite checked *which* strings
were rendered and *where*, but never what the pixels looked like between the
glyphs. A screenshot (dim overlay + solid text blocks) is worth several hundred
assertions here. Screenshot added to demonstrate problem: `stage6_screenshot.png`

- **All tactical/HUD text rendered as solid filled rectangles.** pygame's
  `Font.render(antialias=True)` returns an `SRCALPHA` surface in which **every
  pixel of the glyph box already carries the text colour** - measured on the
  shipped font: 1765 of 2178 pixels had `alpha == 0` and RGB `(140, 255, 140)` -
  coverage lives only in the alpha byte. The font helper called `.convert()`,
  which converts to the display format *and throws the alpha byte away*, so the
  whole bounding box blitted at full colour: banner, labels, and readouts each
  became an unreadable slab. Measured effect: `convert()` → 4800 banner-coloured
  pixels covering **100%** of the banner's bounding box; `convert_alpha()` → 87
  pixels, **3%**.
  `src/fonts.py::render_text` now uses `convert_alpha()` (fast display-format
  conversion, coverage preserved). The earlier "glyphs wash out toward black, use
  `.convert()`" decision recorded above was based on a misreading of antialiasing
  and is retracted.
- **A cancelled difficulty dialog stayed visible on the title screen.** The user's
  guess - "the title screen is not clearing" - was right in effect, wrong in
  mechanism: `TitleScene.draw()` *did* blit a full-window image every frame, but
  `resources/title_screen.png` was generated on a `SRCALPHA` surface with 3-tuple
  colours on a 4-pixel stride, so three of every four rows were fully transparent
  (2880 of 3840 sampled pixels had `alpha == 0`). A translucent background makes a
  "full-screen blit" into a *composite*: the dialog's panel `(30,30,50)`, its
  border `(100,100,140)`, and its dim overlay stayed stamped under the title
  (10266 dialog pixels measured inside the panel rect after cancelling), and the
  title glyphs re-composited over their own previous frames until they saturated
  to solid white. Three separate guards now exist, because any one of them can
  regress alone:
  1. `scripts/generate_title_screen.py` draws every scanline onto an **opaque**
     surface, and the asset was regenerated.
  2. `TitleScene.on_enter` normalises whatever asset it loads to an opaque surface
     (composited onto the clear colour once at load), so a bad asset can never leak
     through the per-frame blit.
  3. `TitleScene.draw()` fills the window with `_CLEAR_COLOR` before drawing - a
     full-window scene owns the whole window and must repaint, not composite.
- **Test-stride gotcha worth remembering** (this one bit the regression test
  itself): sampling `get_at` on a stride-2 grid makes a *100% filled* box measure
  as 25% coverage. `tests/test_game_flow.py::test_tactical_text_is_readable_glyphs_not_solid_blocks`
  therefore does a coarse pass to find the banner's bounding box and then scans
  that box pixel-by-pixel; with the bug it reports 100%, without it 3%.

## Stage 7 — System graph + map view + fog of war

An interrupted first revision of Stage 7 was reviewed rather than discarded: the
graph generator and the selection/fog rules were sound, so they were kept and
finished. Everything below marked **(fixed)** was broken in that revision and is
now covered by a test. The stage gate grew from 155 to 231 tests
(`tests/test_stage7.py`, 72 tests, plus 5 `map`-section config tests).

- **The `map` config section is `{system_count, connections_min, connections_max,
  alpha_connections}`**, added to the schema (`_MapConfig`), to `base_config()`
  (hence to the `config-factory` fixture) and to all three shipped files in the
  same change. The first revision added the JSON keys *without* the schema: with
  `extra="forbid"` the shipped configs stopped validating and the fixture configs
  lacked the section, so 19 tests failed and `GameScene.__init__` died on
  `KeyError: 'map'` — i.e. the game did not start at all. This is the dev plan's
  "unrecognized config keys are fatal" trap, sprung exactly as warned.
- **Cross-field validation for `map` lives in the config schema, and the generator
  still validates its own output.** Impossible ranges (`connections_min` >
  `connections_max`, `system_count: 27`) are rejected at startup with the key
  named, because a config the loader accepts but the generator cannot build would
  otherwise fail mid-session at "New game". `GraphConstraints.check()` duplicates
  a little of that on purpose: the generator must be usable without the loader
  (tests, tooling, a future save-game path).
- **The 26 system names stay in code** (`NATO_SYSTEMS`), per the spec's rule that
  enum-like IDs do not belong in config. Only their *count* and their connections
  are configurable. **(fixed)** The roster contained "Kiwi" — that is not a NATO
  word; it is "Kilo". "Juliett" (two t's) and "Xray" (one word) are kept because
  they are the NATO spellings, and that looks like a typo, so it is written down.
- **Topology invariants are checked against a `GraphConstraints` value object, not
  hard-coded constants.** **(fixed)** `SystemGraph.validate()` previously asserted
  "26 systems, degree 1..3, Alpha→Bravo/Charlie/Delta" as literals while the
  generator accepted `system_count`/`connections_*` from config, so the knobs were
  decorative and any change to them crashed the game (`ValueError: Alpha must
  connect to Bravo, Charlie and Delta` for `connections_max: 2`). Now the
  generator and the checker are held to the same object, and the property tests
  assert against the constraints they generated with.
- **`connections_min` is enforced by a third generation phase** that gives every
  under-connected system an extra lane, and raises `GraphGenerationError` when the
  request is unsatisfiable (e.g. `min=max=3` over 5 systems: an odd degree sum
  cannot exist). The first revision stored `connections_min` and never used it.
  Consequence worth knowing: with the shipped `connections_min: 1`, a 26-system
  world has exactly 25 edges — a **spanning tree with no route redundancy**, so
  there is exactly one route back to Alpha. That satisfies the spec's "degree ∈
  [1,3]" and is left as the shipped default; raising the min to 2 in config is the
  knob for a world with alternative routes (and is tested).
- **Every RNG draw in the generator comes from a list in `NATO_SYSTEMS` order,
  never from set or dict iteration order.** **(fixed — this is the nastiest bug in
  the revision)** Phase 2 picked an attachment source out of a `set`, and Python
  randomises string hashing per process, so the *same seed produced a different
  world in every run* (three runs of seed 42, three different graphs). Invisible
  inside one pytest process; fatal for replaying a saved world. Regression test:
  `test_generate_withTheSameSeedAcrossHashSeeds_shouldProduceIdenticalAdjacency`
  generates the graph in three child processes with different `PYTHONHASHSEED`
  values and compares digests.
- **The world (graph *and* layout) is owned by `GameScene`/`SystemMapState`, not by
  the map screen.** `SystemMapState` holds the immutable `SystemGraph`, the
  immutable `MapLayout`, and the mutable fog/selection state, and exposes
  `visible_nodes()` / `visible_edges()`. The view draws exactly what it is told.
  *Rejected alternative:* let `MapView` compute its own node ring and re-derive
  visibility in a nested loop over all 26 systems — that is what the first
  revision did, and it both re-laid-out the world on every modal open (spec:
  "layout computed once per game and cached") and drew all 26 node circles
  regardless of reveal state, so the entire map was visible on turn one. The test
  `test_openingAndClosingTheMap_shouldNeverRegenerateTheWorld` counts
  `build_map_layout` calls; `test_draw_withUnrevealedSystems_shouldNotPaintTheirCircles`
  counts pixels.
- **`MapLayout` carries the geometry the renderer *and* the click test use**
  (positions, label anchors, measured label sizes, derived label boxes, hit
  radius). One rectangle per label, agreed on by both sides, so a label you can
  see is a label you can click.
- **Placement is one evenly-spaced ring, ordered by depth-first preorder from
  Alpha.** A degree-≤3 tree placed this way puts each subtree in one contiguous
  arc, so edges drawn as chords never cross — measured at **0 crossing pairs per
  world across 40 seeds**, versus ~59 with the alphabetical ordering the first
  revision used. The placement math is unchanged from `circular_positions`, so it
  stays trivially testable.
- **Labels sit radially outside their node, each at its own offset, and the offset
  is solved per angle.** "Half the label height plus a gap" is the intuitive rule
  and it is wrong everywhere except 12 and 6 o'clock: a 64×14 label at the 3
  o'clock slot reaches 32 px back towards its own node, so a 24 px circle 18 px
  away is *inside* the label's bounding box. `label_offset_for_angle()` bisects on
  the true point-to-box distance.
- **The label font size is the largest that verifiably fits, and the bound is
  worst-case over *any* ring ordering.** Two guards, both needed:
  `overlapping_pairs()` on the layout that was built (necessary) and
  `_labels_clear_adjacent_slots()` requiring the two widest names to fit side by
  side at the tightest point of the ring (sufficient for every world). Without
  the second guard, verifying only the built layout accepted 20 pt for some seeds
  and 14 pt for others — the map's typography would have drifted from world to
  world.
- **Overlap checks use the geometry things are actually drawn with**: label/label
  is box-vs-box, node/node is circle-vs-circle, label/node is circle-vs-box. A
  bounding-square test for the circles demands clearance no 1024×768 window can
  afford (it pushes the label ring off screen), and it also produced 3200 false
  positives while being written.
- **`HEADER_BAND` (72 px) is part of the layout contract**, so the modal's own
  copy (banner, `Current: X  Destination: Y`, hint line) can never collide with a
  system label: `fits_on_screen()` treats the band as a hard edge. Without it the
  ring's topmost label lands at y≈16, straight through the header text.
- **`MapLayoutError` is raised when no font size fits** (e.g. a 120×120 window).
  A silently cramped map is worse than a named failure.
- **Hit testing lives in the layout** (`MapLayout.node_at`): a click counts if it
  lands in a node's hit circle *or* in that node's label box, and only
  *revealed* systems are candidates — so fog of war is enforced at the pick level,
  not only in the renderer. The hit radius is 45% of the node-to-node gap, so two
  nodes can never both claim one click.
- **Toggle-off is tested before selectability in `handle_map_click`.** **(fixed)**
  An already-selected system is still a perfectly legal selection target, so
  `can_select` first re-selected it forever and the spec's toggle-off was
  unreachable code. Every rule passed in isolation; only a two-click test sees it.
- **`SystemMapState` refuses a `MapLayout` from a different world** by comparing
  the layout's placement order with a recomputed preorder of its graph. Two
  worlds contain the same 26 names, so a name-set comparison passes while the
  coordinates belong to another topology — every click would select the wrong
  system with nothing visibly wrong.
- **A full-window scene repaints the whole window.** `MapView.draw()` fills the
  surface before drawing (same rule as `TitleScene` in the manual-fixes section).
  **(fixed)** The first revision never cleared, so the tactical view, HUD and
  minimap showed straight through the "modal". Regression test paints the canvas
  magenta and asserts zero magenta pixels survive (exact aligned scan, because the
  stride-2 sampling gotcha in the manual-fixes section makes coverage counts lie).
- **Each label gets a background-coloured halo before its glyphs are blitted.**
  With the shipped tree graph, DFS placement keeps every edge out of every label
  box (measured: 0 intersections across 25 worlds), but a config that raises
  `connections_min` adds cycle edges that would cut a strikethrough through a
  name. One rect is cheaper than auditing every future edge for it.
- **The current system is drawn green and the map prints a header line.** The spec
  asks for "white circles + labels + thin grey edges"; a map with no "you are here"
  marker and no destination readout is unusable, so the additions are recorded
  here rather than smuggled in. Selection still uses the spec's `[ ]` brackets
  (rendered as real glyph brackets hugging the label box, not hand-placed rects).
- **`J` is not Stage 7's business.** The map sets a destination and the HUD nav
  line reflects it (`No destination` → `Hyperspace / Bravo`, the Stage 6 seam), but
  `J` still does nothing until Stage 8 builds the jump animation. The header hint
  mentions J; a player who presses it gets nothing, which is expected for this
  stage.
- **Two jump flags, deliberately separate.** `GameState.is_jumping`
  (`begin_jump`/`end_jump`) is model state the map gate consults;
  `InputLayer.locked` suppresses controls. The map gate needs a *queryable* state
  that survives an input drain, and Stage 8 owns setting both. Recorded because
  they look duplicative.
- **The simulation is paused while the map is open** — `SceneManager` routes
  `update()` to the top scene only (Stage 6 review fix 1). That is the modal
  semantic the stack exists for; `test_simulationStaysFrozenWhileTheMapIsOpen`
  pins it so a future "update every scene" change cannot quietly make the map a
  real-time overlay.
- **`MapView(state)` takes only the map state; the manager arrives via
  `on_enter`.** **(fixed)** The first revision's signature was
  `MapView(manager, state)` but `GameScene` passed *itself*, and `on_enter` then
  overwrote the attribute — so `self._manager.pop()`, `.quit()` and `.audio` were
  being called on a `GameScene` that has none of them, and only the accidental
  overwrite kept it working. Related cleanups: `GameScene` no longer reaches into
  `manager._stack` (only the top scene is updated, so a "map already open" guard
  is dead code), the bogus "avoid a circular import" local re-import is gone, and
  `TacticalView.update()` / `GameScene.update()` now return typed actions.
- **`GameScene.draw()` syncs `hud.nav_selected_name` from the map state** rather
  than doing it in `update()`: `update()` does not run while a modal is on top,
  but `draw()` always does, so a destination chosen on the map would otherwise
  only appear on the HUD after closing it. Mutating in `draw()` is a small smell;
  the alternative (the HUD reaching into the map state) is worse coupling.
- **`tests/test_zz.py` was deleted**: a leftover Stage 6 debug probe
  (`test_debug_colors`, printing sampled colours), not a Stage 7 test.
- **connections_min** ships with default **2**, not 1. The spec calls for
  each node to have a minimum of 1 connection, but this can lead to more
  tedious exploration (have to traverse back to Alpha to explore another branch).
  Shipping with default of 2 in all three configs makes inter-system jumping easier.
- **Gotchas for the next stage.** (1) The graph is seeded from a *separate*
  `random.Random(config["rng"]["seed"])` — a world seed — while `GameState.rng` is
  still unseeded; `rng.seed` does not yet reproduce a whole playthrough, only the
  world. Stage 9/10 RNG work should decide whether to thread one generator
  through. (2) Layout geometry is baked for the non-resizable 1024×768 window; if
  resizing ever lands, the layout must be rebuilt on resize. (3) With `min=1` the
  ring's DFS ordering still draws a few long "spoke" edges across the middle of
  the map: correct, uncrossed, but visually busy — a radial/tree layout is the
  upgrade path if that ever bothers a human.
